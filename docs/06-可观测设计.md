# 06 · 可观测设计

> 「可观测」在本项目里不是运维附属品，而是**产品差异化卖点**：用户能实时看到 Agent 在检索什么、调用什么模型、每一步花了多久。
> 本篇给出事件协议、传输层、前端消费三层的完整设计。

---

## 1. 设计目标

### 1.1 要解决什么问题

Agent 类产品最大的体验问题是**黑盒感**：用户点了按钮，界面转圈十几秒，然后突然出现结果。这十几秒里发生了什么，用户完全不知道，也无从判断「是模型慢、还是检索没找到东西、还是反复重试了」。

### 1.2 三条设计原则

| 原则 | 含义 | 反面做法（刻意避开） |
|---|---|---|
| **每一步都可见** | Agent 的每个动作（模型调用 / 向量检索 / 工具调用）都产出结构化事件 | 只在最后返回一个结果 |
| **不暴露思维链** | 推的是「做了什么、耗时多少」，**不是模型的推理文本** | 把模型的思考过程原样打给用户 |
| **同一事件原地更新** | 一个步骤只有一行，从「进行中」变成「已完成 + 耗时」 | 开始推一条、结束再推一条，面板里出现两行 |

### 1.3 用户实际看到的样子

```
模型  generate:1        出题 · deepseek-v4-flash · 第 1 次尝试      2.3s  ✓
检索  retrieve:向量化   向量化 · BGE-M3                             0.04s ✓
检索  retrieve:召回     向量召回 · 命中 5 条                         0.01s ✓
检索  retrieve:精排     精排 · bge-reranker-v2-m3 · 保留 5 条         0.18s ✓
检索  dedup:1          查重 · 最高相似度 0.93 · 阈值 0.9 · 判定：与题库重复，重新生成
模型  generate:2        出题 · deepseek-v4-flash · 第 2 次尝试      2.1s  ✓
检索  dedup:2          查重 · 最高相似度 0.41 · 阈值 0.9 · 判定：通过
```

这段轨迹同时服务三个人：用户（知道系统在认真干活）、开发者（定位性能瓶颈）、答辩评委（一眼看懂 Agentic 的「决策」在哪里）。

## 2. step event 协议

### 2.1 事件结构（固定 5 个字段）

```python
{
    "id": step_id,           # 步骤标识，同一逻辑步骤的 running 与 done 用同一个 id
    "type": kind,            # 事件类型："模型" / "检索" / "工具" / ...
    "status": "running" | "done",
    "payload": {...},        # 业务载荷，键名用中文（面向展示）
    "duration_ms": int | None,   # running 时为 None，done 时为耗时
}
```

### 2.2 推送机制

节点内通过 LangGraph 的 stream writer 主动推送：

```python
def _push(event: dict) -> None:
    """把事件实时推给 SSE 流。非图内运行时没有 stream writer，静默忽略。"""
    try:
        get_stream_writer()(event)
    except Exception:
        pass

def _start(step_id: str, kind: str, payload: dict) -> None:
    """节点开始执行：立即推送一条「进行中」事件。"""
    _push({"id": step_id, "type": kind, "status": "running",
           "payload": payload, "duration_ms": None})

def _finish(traces: list[dict], step_id: str, kind: str, payload: dict,
            duration_ms: int) -> None:
    """节点执行完成：推送并记录一条「已完成」事件（与 _start 同 id）。"""
    event = {"id": step_id, "type": kind, "status": "done",
             "payload": payload, "duration_ms": duration_ms}
    traces.append(event)
    _push(event)
```

**`_push` 吞异常是刻意的**：非流式调用路径下没有 stream writer，`get_stream_writer()` 会抛异常，但这属于正常情况。吞掉它，让同一份节点代码在流式与非流式两条路径下都能跑。

**`_start` 推 running、`_finish` 同时推 done 并 append 到 `traces`** —— 这是两个独立动作：`traces` 服务于非流式路径（一次性返回轨迹数组），`_push` 服务于流式路径（实时推送）。

### 2.3 事件类型全集

| type | 含义 | payload 关键字段 |
|---|---|---|
| `模型` | 一次 LLM 调用 | 工具名、模型名、第几次尝试 / 第几轮 |
| `检索` | 一次检索步骤 | 阶段、候选数 / 命中数、模型名 |
| `工具` | 一次工具调用 | 工具名 |
| `结果` | 最终业务结果 | 各图 output |
| `错误` | 异常 | message |
| `token` | 对话文本分片 | text |
| `hr_message` | 一整句 HR 回复 | content、turn |
| `session` | 面试会话 id | session_id |
| `已记录` | 评分落库回执 | answer_id、is_wrong |

> `token` 事件的 payload 只有 `{text}`，**没有 `status` 与 `duration_ms` 字段** —— 它是流式分片，不是「步骤」。`hr_message` 只有 `payload`，且**不上抛给前端**（由服务端消费后写库，见 §5.3）。

### 2.4 step_id 命名规则

| 来源 | id 形式 | 例子 |
|---|---|---|
| 出题生成节点 | `generate:{尝试次数}` | `generate:1`、`generate:2` |
| 出题查重节点 | `dedup:{尝试次数}` | `dedup:1`、`dedup:2` |
| 其余图节点 | 固定串 | `grade` / `followup` / `parse_resume` / `parse_jd` / `diagnose` / `interview_question` / `interview_report` / `training_report` |
| 检索内部 | `retrieve:{阶段}` | `retrieve:向量化` / `retrieve:召回` / `retrieve:稀疏` / `retrieve:融合` / `retrieve:精排` |
| 简历 PDF 抽取 | 固定串 | `pdf_extract`（在 API 层推，不在图内） |
| 面试 HR 回复 | `hr_reply:{轮次}` | `hr_reply:1`、`hr_reply:2` |

**为什么出题用带尝试次数的 id**：因为查重不过会重新生成，第 1 次和第 2 次的生成是两个独立的步骤，必须各有独立 id 才能各占一行。而其余节点在一次执行中只跑一次，用固定串即可。

**为什么检索的阶段要分开 id**：因为一次检索内部有多个阶段（向量化 / 召回 / 精排），用户需要看到「是嵌入慢还是检索慢」。

## 3. 双流分工：`custom` 与 `updates`

### 3.1 实现

```python
async def _stream(g, initial: dict, runtime: dict | None = None):
    """流式执行图，实时产出可观测事件，供 SSE 推送。"""
    initial.setdefault("traces", [])
    if runtime:
        initial = {**runtime, **initial}   # 业务入参优先
    final = None
    try:
        async for mode, chunk in g.astream(initial, stream_mode=["custom", "updates"]):
            if mode == "custom":
                yield chunk                     # 实时事件，直接转发
                continue
            for _node_name, update in chunk.items():
                if "output" in update:
                    final = update["output"]    # 只取最后一个含 output 的节点
    except Exception as exc:
        yield {"type": "错误", "payload": {"message": str(exc)}}
        return
    if final is not None:
        yield {"type": "结果", "payload": final}
```

### 3.2 两条流的分工

| 流 | 内容 | 处理方式 |
|---|---|---|
| `custom` | 节点内 `_start` / `_finish` 主动推的事件（含「进行中」状态） | **直接 `yield`，不做任何转换** |
| `updates` | 每个节点执行完后的 state 增量 | **只用来抓最终结果**，逐节点遍历，谁带 `output` 键就覆盖 |

### 3.3 三个关键设计细节

**细节一：轨迹不从 `updates` 取**

`updates` 流里其实也有节点返回的 `traces` 列表，但**刻意不用** —— 因为 `custom` 通道已经推过同样的事件，两边都取会导致每条轨迹出现两次。这是一个「宁可少用一个数据源，也要避免重复」的选择。

**细节二：`结果` 以「最后一个含 output 的节点」为准**

```python
for _node_name, update in chunk.items():
    if "output" in update:
        final = update["output"]
```

循环会覆盖 `final`，所以最终留下的是**最后一个**带 `output` 的节点。这个设计正好解决出题判重的场景：第 1 次生成被判重复后回边重生成，第 2 次的 `output` 会覆盖第 1 次 —— **中间产物既不推送也不落库**，用户只看到最终的题。

**细节三：异常不抛给 StreamingResponse**

```python
except Exception as exc:
    yield {"type": "错误", "payload": {"message": str(exc)}}
    return
```

因为此时 HTTP 响应头已经发出（状态码 200），无法再改成 500。所以异常必须**降级成一条 `错误` 事件**，让前端通过事件流感知失败。

### 3.4 流式路径下 `traces` 被丢弃

| 路径 | 轨迹怎么回去 |
|---|---|
| 流式（`_stream`） | 靠 `custom` 通道的实时事件；state 里的 `traces` **最终被丢弃**（`_stream` 不读它） |
| 非流式（`_invoke`） | `{"output": ..., "traces": result.get("traces", [])}` —— `traces` 随响应体一次性返回 |

所以 `_finish` 里的 `traces.append(...)` 在流式路径下是「无用功」但无害。保留它是因为同一份节点代码要同时服务两条路径。

### 3.5 非流式路径的线程池包装

```python
await asyncio.to_thread(_invoke, graph.xxx, {...}, runtime)
```

`graph.invoke` 与本地 embedding / rerank 都是**同步阻塞调用**。直接 await 会把事件循环卡住，导致其他请求无法响应。扔进线程池是必要的。

## 4. SSE 传输层

### 4.1 封装（`app/api/sse.py`，全文 25 行）

```python
_SSE_HEADERS = {
    "Cache-Control": "no-cache",
    "Connection": "keep-alive",
    "X-Accel-Buffering": "no",   # nginx 等反向代理据此关闭响应缓冲
}

def sse_response(gen) -> StreamingResponse:
    """将异步事件生成器包装为 SSE 响应，流末尾补一个 [DONE] 标记。"""
    async def event_stream():
        async for event in gen:
            yield f"data: {json.dumps(event, ensure_ascii=False)}\n\n"
        yield "data: [DONE]\n\n"

    return StreamingResponse(
        event_stream(), media_type="text/event-stream", headers=_SSE_HEADERS
    )
```

### 4.2 三个 header 的作用

| header | 作用 | 不设的后果 |
|---|---|---|
| `Cache-Control: no-cache` | 禁止缓存 | 中间层可能缓存整个响应 |
| `Connection: keep-alive` | 保持长连接 | 连接可能被提前关闭 |
| **`X-Accel-Buffering: no`** | **告诉 nginx 等反向代理不要缓冲** | 事件被代理攒起来批量下发，实时性完全丧失 |

`X-Accel-Buffering` 是最容易被忽略但最关键的一个。SSE 的实时性依赖「产生一条就送一条」，任何中间层缓冲都会破坏它。

### 4.3 协议选择：匿名 `data:` 帧

| 项 | 本项目的选择 | 说明 |
|---|---|---|
| 命名事件（`event:` 行） | **不用** | 所有事件都是匿名 `data:` 帧，靠 JSON 体里的 `type` 字段区分 |
| 事件 id（`id:` 行） | **不用** | 不需要断线重连后按 id 续传 |
| `retry:` 行 | **不用** | 不依赖浏览器自动重连 |
| 心跳注释帧 | **不用** | **无心跳**，长静默期可能被中间层断开（已知边界） |
| 结束标记 | `data: [DONE]\n\n` | 注意是**包在 `data:` 里的字符串**，不是裸的 `[DONE]` |
| 序列化 | `json.dumps(..., ensure_ascii=False)` | 中文不转义成 `\uXXXX`，便于调试时直接看日志 |

**为什么不用 EventSource**：浏览器的 `EventSource` 只支持 GET 且不能自定义请求头，而本项目的流式端点全是 POST 且需要 `Authorization: Bearer`。因此前端用手写的 `fetch` + 流式读取实现（见 §5）。

### 4.4 无心跳是一个已知边界

SSE 流在长静默期（例如模型思考了很久没吐 token）没有任何数据发送。此时中间的代理或负载均衡可能判定连接空闲并断开。

**一期未处理的原因**：开发环境是前端直连后端，中间没有代理，不会触发。生产环境部署在 nginx 后面时需要补心跳注释帧（`: ping\n\n`）。已记录为演进项。

## 5. 前端消费

### 5.1 流式解析

前端不用 `EventSource`，而是手写 `fetch` + 流式读取：

```ts
const reader = res.body.getReader();
const decoder = new TextDecoder();
let buffer = "";
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const chunks = buffer.split("\n\n");     // 以空行为事件边界
  buffer = chunks.pop() ?? "";             // 最后一段可能不完整，留到下一轮
  for (const chunk of chunks) {
    const line = chunk.trim();
    if (!line.startsWith("data:")) continue;
    const data = line.slice(5).trim();
    if (data === "[DONE]") return;         // 终止哨兵
    try { yield JSON.parse(data) as StreamEvent; } catch { /* 跳过无法解析的事件 */ }
  }
}
```

**四个必须处理的细节**：

| 细节 | 处理方式 | 不处理的后果 |
|---|---|---|
| 事件边界 | 按 `\n\n` 切分 | 无法区分多个事件 |
| 跨 chunk 截断 | 用 `buffer` 暂存最后一段不完整数据 | 一个事件被 TCP 分片后解析失败 |
| 中文多字节截断 | `decoder.decode(value, { stream: true })` | 中文字符被从中间切开变乱码 |
| 解析失败 | 静默跳过该事件 | 一个坏事件导致整个流中断 |

### 5.2 状态机：`useAgentRun`

```ts
useAgentRun(storageKey?) → { traces, running, error, setError, run }
```

`run(events, onResult, { reset, onEvent })` 的执行分支（顺序即优先级）：

| 事件 | 处理 |
|---|---|
| `type === "错误"` | 设置 error，调 `onEvent`，然后 **break**（终止循环） |
| `type === "结果"` | 调 `onResult`，调 `onEvent`，**continue**（不进面板） |
| `CHAT_EVENTS.has(type)` | 只调 `onEvent`，**continue**（不进面板） |
| 其余 | 调 `onEvent`，然后按 key 在 traces 中**原地替换**；找不到就 append |

### 5.3 关键设计一：合并键带「运行序号」

```ts
const seq = ++runSeq.current;
const key = event.id ? `${seq}:${event.id}` : undefined;
```

合并键是 **`{运行序号}:{节点 id}`**，而不是单纯的节点 id。

**为什么必须带序号**：同一个页面上多次执行会调用同一个节点。例如模拟面试的第 1 / 2 / 3 轮都会跑 HR 回复（`hr_reply:1` / `hr_reply:2` / `hr_reply:3` 已经有轮次区分），但更典型的是**同一个页面反复点「出题」** —— 每次都是 `generate:1`。如果只按 `generate:1` 做键，第二次执行会把第一次的轨迹覆盖掉，面板里看起来像「什么都没发生」或者「轨迹错乱」。

加上运行序号后，每次 `run()` 都是独立的命名空间，多次执行的轨迹可以共存。

### 5.4 关键设计二：对话事件不进面板

```ts
/** 这些事件是对话内容，不进执行面板（token 是逐字分片，混进轨迹会刷屏）。 */
const CHAT_EVENTS = new Set(["token", "session", "hr_message"]);
```

| 事件 | 为什么不进面板 |
|---|---|
| `token` | 逐字分片，一条回复会产生几十上百个事件，混进面板会把轨迹冲得看不见 |
| `session` | 是会话元信息，不是「步骤」 |
| `hr_message` | 与 `token` 拼出的完整内容重复 |

这些事件通过 `onEvent` 回调交给页面自己处理（把 token 拼成气泡）。**同一个 `useAgentRun` 同时服务两类事件流**：面板要的步骤事件与页面要的对话事件，靠 `CHAT_EVENTS` 分流。

### 5.5 关键设计三：轨迹跨路由保留

`useAgentRun(storageKey)` 传入 storageKey 后，轨迹 key 变成 `${storageKey}:traces`，初值从 `getPageState` 恢复。

这样「执行面板的轨迹」与「页面主体状态」一起被 `usePageState` 的机制保留 —— 切走再回来轨迹还在。这与 [02-总体架构设计.md](./02-总体架构设计.md) 提到的 App Router 卸载问题共用一套解法。

## 6. 事件类型 × 模块对照表

| 模块 | 推的事件 | 流式端点 |
|---|---|---|
| **出题** | `retrieve:向量化` → `retrieve:召回` → `retrieve:稀疏`/`融合`/`精排` → `generate:{n}` → `dedup:{n}` → `结果` | `POST /training/question/stream` |
| **评分** | `retrieve:*` → `grade` → `结果` → `已记录` | `POST /training/grade/stream` |
| **追问** | `followup` → `结果` | `POST /training/followup/stream` |
| **简历解析** | `pdf_extract` → `parse_resume` → `结果` | `POST /resume/parse/stream` |
| **简历诊断** | `pdf_extract`? → `parse_resume` → `parse_jd` → `diagnose` → `结果` | `POST /resume/diagnose/stream` |
| **面试提问**（独立端点） | `interview_question` → `结果` | `POST /interview/question/stream` |
| **面试对话** | `session` → `hr_reply:{turn}` + N×`token` → `结果` | `POST /interview/chat/stream` |
| **面试报告** | `interview_report` → `结果` | `POST /interview/report/stream` |
| **训练报告** | `training_report` → `结果` | `POST /report/training/stream` |

**9 个流式端点，全部走同一套 `sse_response` 与同一份事件协议。** 前端不需要为任何模块写特殊逻辑（除了用 `CHAT_EVENTS` 分流对话事件）。

## 7. 轨迹归档（规划）

### 7.1 现状：刷新即丢

| 存储位置 | 存活范围 | 问题 |
|---|---|---|
| SSE 事件流 | 请求期间 | 请求结束即消失 |
| 前端 `sessionStorage`（经 `usePageState`） | 当前标签页 | 关掉标签页即清空 |
| 服务端 `tool_traces` 表 | **表已建，无写入** | 完全没有落库 |

**所以「可回溯」（FR-F3）目前只做到一半**：同一次会话内切路由能保住，刷新能保住（同一标签页），但关掉标签页或换设备就没了。

### 7.2 规划方案：接入 Langfuse

`langfuse>=2.30` 依赖已经声明，但**代码零引用**。接入的价值有三：

| 价值 | 说明 |
|---|---|
| **轨迹可回看** | 从「刷新即丢」变成可按会话、按用户、按时间查询 |
| **成本看板** | 每次训练 / 面试消耗多少 token、花多少钱，可按用户与模块聚合 |
| **延迟分析** | 每个步骤的耗时分布，定位慢在哪一环（模型慢还是检索慢） |

### 7.3 接入落点

| 落点 | 做什么 |
|---|---|
| `app/api/sse.py` 或 `agent/service.py` | 在事件推给前端的同时，异步上报一份到 Langfuse |
| LangGraph 节点 | 可选的 span 埋点，让轨迹带上节点层级 |
| 管理后台 | 新增「轨迹与成本」页，按会话 / 用户 / 模块查看 |

**为什么不直接落 `tool_traces` 表**：那张表的设计（`session_id` 是 `String(64)` 且无外键、`step` 是自增序号、`payload_json` 存整块）适合「按会话线性回放」这一种查询模式，不适合成本聚合、延迟分位数、跨模块对比这些分析型查询。Langfuse 本身就是为 LLM 可观测设计的，直接用它比自建表更省事。

## 8. 为什么不用 Next.js rewrites 代理

这是本项目**实测踩坑**得出的结论，值得单独记录。

### 8.1 现象

早期配置 `next.config.mjs` 的 `rewrites` 把 `/api/*` 代理到后端 8000 端口，期望解决跨域问题。结果是：**执行面板在请求期间一动不动，请求结束后所有事件一次性全出现**；面试的 HR 回复同样从「逐字流式」退化成「整段一次性出现」。

### 8.2 根因

Next.js 的 rewrite 是一个**服务端代理**。它收到后端的 `text/event-stream` 响应后，会先**把整个响应体读完**再转发给浏览器 —— 也就是对 SSE 做了缓冲。SSE 的全部价值建立在「产生一条推一条」上，被缓冲之后与普通 JSON 响应没有区别。

### 8.3 解法

前端**直连**后端（`frontend/.env.local` 的 `NEXT_PUBLIC_API_BASE`），跨域由后端 `CORSMiddleware` 放行：

```python
app.add_middleware(
    CORSMiddleware,
    allow_origin_regex=r"http://(localhost|127\.0\.0\.1)(:\d+)?",
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

### 8.4 顺带解决的一个问题：为什么用正则而不是端口列表

用 `allow_origin_regex` 而不是 `allow_origins=["http://localhost:3000", ...]`，原因是 **Next 开发服务器在 3000 被占用时会自动顺延到 3001 / 3002**。固定列表会让新端口上的前端每个请求的 CORS 预检都返回 400「Disallowed CORS origin」，且这个错误看起来像后端故障，排查成本很高。

**注意**：`allow_credentials=True` 时不能用 `allow_origins=["*"]` 通配。正则方案同时满足「允许任意本地端口」与「不使用通配符」两个约束。

**生产环境必须收紧成真实前端域名** —— 这一点在代码注释里已明确标注。

## 9. 本篇小结

| 设计点 | 技术含量 |
|---|---|
| 同 id 原地替换 | 用 id 语义把「步骤」与「事件」区分开，前端只需一次替换逻辑，不用维护「正在执行的行」 |
| `custom` / `updates` 双流分工 | 从两个数据源里选一个取轨迹、另一个只取结果，避免重复；顺带让「查重重生成」的中间产物自然被忽略 |
| `CHAT_EVENTS` 分流 | 同一套事件机制同时服务「步骤面板」与「对话气泡」两种截然不同的 UI |
| 合并键带运行序号 | 一行代码解决「同页面多次执行轨迹互相覆盖」的问题 |
| `_push` 吞异常 | 让同一份节点代码在流式与非流式两条路径下都能运行 |
| 异常降级为事件 | 认识到「HTTP 头已发出就改不了状态码」，主动把异常转成业务事件 |
| `X-Accel-Buffering` | 一行 header 决定 SSE 在生产代理后面是否还有意义 |
| 不用 rewrites | 从「面板不动」这个现象定位到代理缓冲这个根因 |
