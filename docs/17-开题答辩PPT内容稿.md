# 第 2 页 · 痛点与改进

**评分点：问题与范围 15 分**（用户与任务 / 现成对比对象 / 真实痛点 / 拟改进点 / 不足 / 首版边界）

## 2.1 现成方案与使用场景

**用户与任务**：计算机专业在校生/应届生，在准备秋招/实习时，需要**针对某个技术方向、某个难度**练习八股与算法题，并知道自己**差在哪、怎么改**。

**现成对比对象（三个，都是我们真实用过或在用的）**：

| 方案 | 谁在什么情况下用 | 我们的试用结论 |
|---|---|---|
| **牛客网题库**（nowcoder.com） | 计算机学生按公司/岗位刷专项题 | 题是**静态的**；做完只有对错，**不给针对我的评价**；同一岗位刷第二遍，题还是那几道 |
| **力扣**（leetcode.cn） | 算法专项训练 | 算法题没有标准答案的自评能力；**八股完全覆盖不到** |
| **直接问 ChatGPT / DeepSeek** | 临时问一个概念 | 是**黑盒**：看不到它依据什么；给的是**通用答案**，不是「这个方向这个难度」的参照；评分不可解释 |

> 行业趋势佐证：牛客 HR《2025 秋招破局：AI 面试如何重塑企业人才筛选逻辑》——求职者「被 AI 面试」已成常态，反向催生「用 AI 练习面试」的需求。

## 2.2 实际遇到的痛点（一个具体例子）

**场景**：我们组同学在准备后端岗，刷完牛客「MySQL 索引」专项后问 DeepSeek「我这块能拿几分」，模型回了 3 分和一段「建议多练」。

**四个具体缺口**：

| # | 缺口 | 现场表现 |
|---|---|---|
| 1 | **黑盒** | 看不到模型检索了什么、依据哪份资料 |
| 2 | **无参照** | 给的是通用知识，不是「这个方向 + 这个难度」的参考答案 |
| 3 | **评分不可解释** | 说「3 分」，但不知道扣在正确性、完整性、表达还是术语 |
| 4 | **无追踪** | 对话结束就没了——没有错题本、没有复习计划、没有能力画像 |

## 2.3 本组准备怎样改进

**改哪一步**：把「一次性问答」改成**有参照 + 有量表 + 有记忆的闭环**。

| 改动 | 具体做法 | 预期变化 |
|---|---|---|
| **加参照** | 出题/评分前先检索题库库（BGE-M3 向量 + rerank），用**检索到的参考答案**约束生成 | 回答有出处，不再是通用知识 |
| **加量表** | 四维 rubric（正确性 0.40 / 完整性 0.30 / 表达 0.15 / 术语 0.15，各 0–5），**每维必须给 reason** | 分数可解释、可审计 |
| **加记忆** | 错题进 SM-2 复习排期；每次作答更新能力画像 | 下次出题贴着薄弱点走 |
| **加透明** | 每一步（模型调用 / 向量检索 / 工具）以 SSE 推给前端「执行面板」 | 从黑盒变成**看得见的过程** |

## 2.4 当前不足与取舍

**如实说明（这是本节的得分点，不是减分项）**：

| 不足 | 现状 | 取舍理由 |
|---|---|---|
| **题库规模小** | 种子题仅 **12 条**（后端 6 / 前端 3 / 算法 3） | 首版先跑通**入库→检索→去重→出题→评分**全链路；补齐计划见第 3 页 |
| **面经企业库未实现** | PRD 规划的三个知识库，目前**只落地题库库** | 面经需清洗与授权，且当前**没有可用语料**；列为 P1 |
| **依赖云端生成模型** | 主生成走 `deepseek-v4-flash` 云端端点，有网络延迟与按量费用 | 本地 vLLM 方案已写好脚本（第 4 页），**待有 GPU 环境落地**；BGE-M3/rerank 已本地 |
| **简历仅解析不留档** | PDF 只提取文本，**未上传对象存储** | 首版聚焦「诊断」能力，不做简历版本管理 |
| **画像靠前端主动更新** | 画像写入由前端在拿到结果后 POST `/report/profile`，**非后端自动触发** | 已定位到改造点，列为 P1 |
| **轨迹刷新即丢** | Langfuse 依赖已声明但**代码零引用**；step event 只推前端实时展示，**刷新就没了**（`tool_traces` 表建了但无读写） | 首版靠「历史记录」存页面快照兜底；轨迹归档列为 P1 |
| **无自动化测试** | 当前**零单元测试、零 `tests/` 目录**，pytest 从未使用；验收靠 `docs/12` 的 **83 步端到端清单**人工跑 | 首版重心在功能闭环；回归测试列为 P1（P0 补 6 个纯函数单测） |
| **工具注册表近乎空壳** | `app/agent/tools.py` 的 `ALL_TOOLS` **只有 1 个工具**（`retrieve_knowledge`），没有真正的 ReAct 工具循环 | 编排是「显式状态图」而非「模型自主选工具」，符合 PRD 的显式建图决策；但工具生态是空壳，已列入规划 |

**首版边界（一句话）**：**一个用户、一个方向、题库库一个知识库、四维评分一个量表**——先把「刷题→评分→错题→复习」这一条链做到可信，不追求全场景覆盖。

## 3.3 标注规则（评分量表怎么定分）

**四维 rubric**（权重固定，量纲 0–5 分）：

| 维度 | 权重 | 0 分 | 5 分 | 中间分判断依据 |
|---|---|---|---|---|
| 正确性 correctness | 0.40 | 与题目完全无关或含硬伤 | 结论全对、推导无误 | 有正确主干但个别细节错 |
| 完整性 completeness | 0.30 | 未覆盖任何要求维度 | 覆盖题目全部要求维度 | 漏 1–2 个要求维度 |
| 表达 clarity | 0.15 | 表述混乱、逻辑不通 | 结构清晰、分点作答 | 能读懂但层次一般 |
| 术语 terminology | 0.15 | 术语错误或未涉及 | 专业术语准确且贴合题目 | 术语基本正确但有口误 |

**总分口径**：`total = 0.40×正确性 + 0.30×完整性 + 0.15×表达 + 0.15×术语`，四舍五入到 1 分。

**一条真实标注样例**（`gold.jsonl` 第 1 条，answer_id=4）：

| 字段 | 值（截断） |
|---|---|
| 题目 | 请解释 HTTP 与 HTTPS 的核心区别…（HTTP 方向） |
| **用户作答** | 「三次握手就是先握手再握手最后握手，具体细节记不清了。」 |
| **模型评分** | 正确性 0 / 完整性 0 / 表达 0 / 术语 0（每维均附 reason） |
| **人工标注** | 正确性 3 / 完整性 3 / 表达 4 / 术语 3，**总分 3.0** |
| **差异原因** | 模型判 0 分，人工判 3 分 —— 模型把「与题目无关」判成 0 分，但这道题是**开放题**，人工认为答不出但方向相关给 3 分。**这正是微调要修的偏差** |

> 上表即第 6 页「评测设计」的**真值来源**，也是「第 5 页最小验证」里「失败/边界案例」的素材。

## 4.2 模型与方法（右上）

| 角色 | 准确模型/组件 | 部署 | 关键方法 |
|---|---|---|---|
| **主生成** | `deepseek-v4-flash`（OpenAI 兼容端点） | **云端** | 结构化输出 `response_format=json_object` + Pydantic 校验 |
| **Embedding** | `BAAI/bge-m3` | **本地**（HF 懒加载 + 双重检查锁） | 1024 维稠密向量 |
| **Rerank** | `BAAI/bge-reranker-v2-m3` | **本地** | 召回后精排 |
| **微调模型** | `Qwen/Qwen2.5-1.5B-Instruct` + LoRA r=16 | 本地训练 → vLLM 起服务 | SFT on 四维 rubric JSON |
| **编排** | LangGraph 8 图 / 12 节点 | 进程内 | ReAct 循环 + 条件路由 + checkpoint |
| **检索** | BGE-M3 → Qdrant → rerank | 本地 | **三种模式可热切换**：dense（稠密）/ sparse（BM25，jieba 中文分词）/ hybrid（**RRF 融合**），见 `app/rag/vectorstore.py:92-218` |

**两个关键技术决策（答辩重点）**：

**① 结构化输出用 `json_object`，不用 function calling。**
DeepSeek 在工具调用模式下**不保证** arguments 是合法 JSON —— 模型只要在字符串里写了未转义的引号，整段 JSON 就废掉，langchain 拿到 `None`，上层报 `'NoneType' object has no attribute 'model_dump'`。**实测约三成概率触发**，报告类长文本尤其容易。`json_object` 由服务端约束解码，必然返回合法 JSON，再由 Pydantic 校验字段。

**② LiteLLM 是原生 SDK，不是 langchain 组件。**
返回对象与 langchain 消息接口不兼容。我们没有实现完整的 LangChain ChatModel 子类，而是写**薄适配器 `LiteLLMChat`**，只对齐真正用到的 `bind()` / `invoke()` / `astream()` 三个方法 —— 上层 `JsonSchemaLLM` **一行都不用改**，网关是纯插入式的。

## 5.3 失败或边界情况（右下，**这是本项的得分点**）

**已复现的真实失败案例（不是假想的）**：

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | **结构化输出报 `'NoneType' object has no attribute 'model_dump'`** | DeepSeek function calling 的 arguments **不保证是合法 JSON**（模型在字符串里写了未转义的引号，整段废掉），**实测约三成概率**，报告类长文本尤其容易 | 改用 `response_format=json_object`（服务端约束解码，必然合法）+ Pydantic 校验 |

| 4 | **待复习队列永远是空的** | 间隔重复改「答对一次就毕业」，但队列按 `is_wrong` 过滤 —— 刚排的复习计划永远不触发（**这个 bug 犯过一次**） | 改为**连续答对 `MASTERED_REVIEWS`=2 次**才移出；SM-2 在 quality<3 时清零重复计数，故 `review_count` 天然等于「连续答对次数」 |

| # | 依据 | 口径 |
|---|---|---|
| 1 | **一致性** | 模型四维分与人工标注**相差 ≤1 分**记为一致；一致率 = 一致条数 / 有效样本数 |
| 2 | **偏差** | 每维 MAE = mean(\|预测分 − 人工分\|)；总分 MAE 同理 |
| 3 | **延迟** | 首 token 延迟 = 发请求 → 收到第一个 token 的墙钟时间；**与总延迟分开统计**（一个决定体感、一个决定吞吐） |
| 4 | **失败处理** | 模型返回非法 JSON / 超时 / 分数越界的样本**不丢弃**，计入「失败率」并单独列出 —— 丢弃会让指标虚高 |

**独立测试样例从哪来**：

| 用途 | 来源 | 隔离方式 | 状态 |
|---|---|---|---|
| **真值（ground truth）** | 本组**人工标注** —— 对每条作答按第 3 页的四维 rubric 独立打分，**两人分别标注，差异 >1 分则第三人仲裁** | 人工标注，**在模型产出之前完成**，避免「按模型输出标注」的循环论证 | **仅 2 条占位样本，需扩到 50 条** |
| **训练集** | 系统 `answers` 表导出的 SFT 样本 | 导出时**按 `answer_id` 黑名单排除测试集 10 条** | ⚠ **该过滤逻辑尚未实现**（见 3.4），已列入第 7 页 P0 |
| **测试集** | 上述 10 条人工标注 | **全程不参与训练与调参** | 待建立 |
| **召回评测集** | 取自 `answers` 表真实作答改写成的 20 条查询 | 与评分评测集**分开**，避免一稿两用 | 待建立 |
| **延迟测试** | 固定长度的合成 prompt | 固定长度保证可比；与质量评测**分开跑**，避免互相干扰 | ✅ 方法已实现（`backend/scripts/bench_llm.py`） |

**验收条件（一句话）**：**10 条独立测试样例上，总分一致率 ≥ 0.75 且总分 MAE ≤ 1.0，同时 JSON 解析失败率 = 0**，则该改进判为「有用」；任一项不达标则**不宣称有效**，回到数据/提示词层继续调。

## 6.3 可选指标（模板小字行）

**选用指标（与痛点直接相关）**：① **评分一致率**（对应痛点「评分不可解释」）② **每维 MAE**（对应「不知道扣在哪」）③ **首 token P50**（对应「等第一个 token 的体感」）④ **QPS**（对应「单请求慢导致吞吐上不去」）⑤ **JSON 解析失败率**（对应「黑盒 + 报错」）。
**不选用**：泛泛的「用户满意度」「准确率」——无法计算口径，也与第 2 页的痛点无直接对应。

## 附：答辩现场问答预案（3 分钟提问）

| 可能的追问 | 建议回答（要点） |

| 「你们和市面上的 AI 面试产品有什么区别？」 | 大部分 AI 面试产品是**一次性生成 N 轮**，不是真对话。我们是**一问一答、HR 按 token 流式**，并且**贴着你的简历深挖**（`interview_chat.py` 是对话生成器，不是 StateGraph） |

| 「一致率 0.78 只有 2 条样本，怎么敢写？」 | **这个数字我们已经从 PPT 上撤掉了**。仓库里的 `test_after.json` 是**演示输出格式的占位产物** —— 它的指标声称一致率 0.75，但文件自己的 `rows` 里预测值全是 0，两者数学上不自洽；它声称的模型 `qwen2.5-1.5b-grader` 也从未训练出来。**我们不引用未实测的数字**，PPT 第 6 页这一栏写的是「待实测」，并给出了 50 条样本上的验收阈值 |
