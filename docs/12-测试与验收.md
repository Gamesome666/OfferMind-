# 12 · 测试与验收

> 本篇如实说明测试资产的实际状况：**已有的是可执行的端到端验收流程与三个离线评测脚本，没有的是单元测试与自动化测试套件**。

---

## 1. 测试策略

### 1.1 分层设计

| 层级 | 测什么 | 本项目现状 |
|---|---|---|
| **单元测试** | 纯函数逻辑（SM-2 调度、RRF 融合、分位数计算、prompt 构造） | ❌ **无** |
| **接口测试** | 每个端点的请求/响应契约、鉴权、错误码 | ❌ **无** |
| **端到端验收** | 起基础设施 → 建表 → 入库 → 全链路走通 | ✅ **有可执行清单**（本篇 §3） |
| **离线评测** | 微调效果、压测性能 | ✅ **有脚本**（`scripts/` 三个脚本） |

### 1.2 现状的诚实说明

**仓库里没有 `tests/` 目录，没有任何 `test_*.py` 文件。** `pytest>=8.0` 只声明在 `pyproject.toml` 的 `dev` 可选依赖组里，从未被使用。

**已实现的替代机制**：

| 机制 | 覆盖范围 |
|---|---|
| 端到端验收清单（§3） | 全部功能链路的连通性 |
| `scripts/bench_llm.py` | LLM 性能与稳定性（QPS、延迟分位数、错误率） |
| `scripts/eval_grader.py` | 评分质量的量化指标（一致率、MAE） |
| 非流式端点 | 定位为「给 curl / 测试用」，提供了不经 SSE 的验证路径 |
| `/docs`（Swagger UI） | 端点的交互式手工验证 |

## 2. 为什么没有单元测试

这不是一个应该被辩护的取舍，但也需要说明实际约束：

| 因素 | 说明 |
|---|---|
| 大量逻辑依赖外部服务 | 出题、评分、报告等核心逻辑都依赖 LLM 调用，单元测试需要 mock 整个 LLM 层，mock 出来的测试验证的是 mock 而不是真实行为 |
| 真正值得单测的纯函数很少 | SM-2 调度、RRF 融合、分位数插值、prompt 构造 —— 加起来只有四五个，且都被端到端流程覆盖 |
| 一期的时间分配 | 在「补全功能链路」与「写测试」之间，优先选择了前者 |

**但这些是理由，不是借口。** 下面这几类逻辑**明确应该被单测覆盖**（列入改进计划）：

| 待测函数 | 位置 | 为什么值得测 |
|---|---|---|
| `sm2_next` | `repositories/answer.py` | 纯函数、分支多（quality<3 / reps 0/1/≥2）、错了会导致复习排期全乱 |
| `rrf_fuse` | `rag/bm25.py` | 纯函数、融合逻辑容易写错名次计算 |
| `percentile` | `scripts/bench_llm.py` | 纯函数、边界情况多（空列表、单元素、p=0/1） |
| `parse_deployments` / `parse_fallbacks` | `agent/gateway.py` | 纯函数、大量容错分支，是「网关配置写坏不拖垮服务」的保证 |
| `build_grade_prompt` | `scripts/export_sft_dataset.py` | 训推一致性的关键，但可以用「与线上模板输出一致」来断言 |
| `_route_after_dedup` | `agent/graph.py` | 出题重试逻辑的路由条件 |

**共同特征**：都是**纯函数**（无 IO、无外部依赖），测试成本极低，但出错后果严重（排期错乱、检索结果错乱、网关失效）。这类函数是单测投入产出比最高的目标。

## 3. 端到端验收清单

> 这是当前实际使用的验证方式。每一步都给出命令与**预期观察结果**。

| # | 步骤 | 命令 | 预期结果 |
|---|---|---|---|

## 4. 已有验证证据

> 以下证据来自仓库中的实际产物，**不是设计描述**。

### 4.1 真实请求日志

`backend/uvicorn.log` 显示后端在 8000 端口处理过真实请求，包括：

| 端点 | 说明 |
|---|---|
| `/api/v1/health` | 健康检查 |
| `/api/v1/auth/login` | 登录 |
| `/api/v1/auth/me` | 取当前用户 |
| `/api/v1/training/question/stream` | **流式出题（SSE 链路真的跑通过）** |
| `/api/v1/training/followup/stream` | **流式追问** |

**这证明前端直连 + SSE 流式 + 认证的完整链路是实际联通过的**，不只是代码写完了。

### 4.2 真实的压测产物

`backend/benchmark/cloud-test.json` 是一次真实的压测结果（8 请求 / 并发 4 / prompt 200 字符 / max_tokens 64），含完整的延迟分位数、QPS、错误率。数据详见 [10-模型部署与网关.md](./10-模型部署与网关.md) §5.5。

**这是全项目唯一一份真实的性能数据。** 它证明压测脚本可用、云端端点连通。

### 4.3 一项需要注意的日志告警

`uvicorn.log` 里有一段 passlib 的告警：

```
(trapped) error reading bcrypt version
AttributeError: module 'bcrypt' has no attribute '__about__'
```

**原因**：passlib 与较新版本 bcrypt 的已知兼容性问题（passlib 尝试读取 `bcrypt.__about__.__version__`，新版 bcrypt 移除了这个属性）。

**影响**：**不影响功能** —— 日志后面紧跟登录成功的 200 响应。passlib 捕获了这个异常并继续工作。

**处理建议**：可以忽略，或固定 `bcrypt` 版本，或迁移到 `pwdlib` / 直接用 `bcrypt` 库。

## 5. 已知的联调遗留问题

| 问题 | 影响 | 状态 |
|---|---|---|
| `/health/ready` **不检查任何依赖** | 就绪探针只返回常量，无法反映数据库 / Qdrant 是否可用 | 已知边界 |

## 6. 测试改进计划

按投入产出比排序：

| 优先级 | 项 | 说明 |
|---|---|---|
| **P0** | 补纯函数单测 | 6 个纯函数（§2 表格），每个不到 20 行测试代码，覆盖排期 / 融合 / 网关解析等高风险逻辑 |
| **P0** | 修依赖清单 | 把 4 个缺失的包装进 `pyproject.toml`，否则「按文档装环境」会失败 |
| **P1** | 接口契约测试 | 用 FastAPI `TestClient` + 测试数据库，覆盖鉴权矩阵（401 / 403 / 404 三类） |
| **P1** | SSE 协议测试 | 断言事件格式（5 字段）、同 id 替换语义、`[DONE]` 结尾 |
| **P2** | CI 流水线 | `ruff check` + 单测 + 接口测试，PR 门禁 |
| **P2** | 压测纳入回归 | 定期跑 `bench_llm.py` 并与基线对比，检测性能回归 |
| **P2** | 端到端自动化 | 把 §3 的 83 步清单中可自动化的部分脚本化（需要 Playwright 或类似工具驱动前端） |

**为什么不把「端到端自动化」排在前面**：83 步里有大量需要人工判断的观察点（「面板里不应出现 token 行」「轨迹都保留」），自动化成本高。先补纯函数单测与接口测试，收益更快。

## 7. 一篇小结

**测试这块的自我评价**：

| 做得好的 | 做得不足的 |
|---|---|
| 端到端验收清单写得足够细（83 步，每步带预期观察），可以直接照着验 | **零单元测试** |
| 三个离线脚本提供**可量化**的评测能力（性能 + 质量），这是很多项目没有的 | 无 CI，无回归门禁 |
| 非流式端点保留了「给 curl 测试用」的定位，提供了不经 SSE 的验证路径 | `/health/ready` 名不副实（不检查依赖） |
| 关键功能的验证里有针对**历史踩坑**的专项检查项（如第 29 步验证 SM-2 毕业规则） | 依赖清单不完整，环境可复现性差 |

**最重要的一条**：验收清单里那些「验证坑 X 的修复没有被回归」的检查项（第 29、77 步等），比「功能是否可用」的检查项更有价值 —— 它们防止的是**已经踩过一次的坑**。
