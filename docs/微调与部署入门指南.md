# 微调与部署入门指南：每一步在做什么、为什么

> 本文面向第一次接触模型微调和部署的同学。目标不是让你背命令，而是让你明白：
> **每一步为什么存在，少了它会出什么问题。**
> 具体命令以 `backend/finetune/README.md` 与 `backend/deploy/README.md` 为准，本文中标出了文档与实际不符的地方。

---

## 0. 先看全局：我们到底在做什么

### 0.1 要解决的问题

OfferMind 里有一个环节：用户答完一道面试题后，系统要给回答打分。这个打分现在交给**云端大模型**（DeepSeek）完成。

云端模型有三个问题：

| 问题 | 具体表现 |
|---|---|
| 贵 | 每次评分都要按 token 付费 |
| 慢 | 首字延迟约 2.7 秒，P99 约 5.5 秒 |
| 不可控 | 服务商改版本、限流、宕机，我们都没法干预 |

所以课程要求的「部署与微调」在这里的落点是：**训练一个本地小模型，让它学会像大模型那样打分，然后把它部署在自己机器上。**

### 0.2 一个类比

把整件事想成「培养一个批改作文的学徒」：

| 类比中的角色 | 项目中对应的东西 | 作用 |
|---|---|---|
| 有经验的老师 | 云端 DeepSeek | 现在负责批改，水平高但贵 |
| 历史批改记录 | `answers` 表里的评分记录 | 老师批过的每一份作业，都带着分数 |
| 学徒 | Qwen2.5-1.5B 小模型 | 要学会老师的批改标准 |
| 学徒跟老师学习 | LoRA 微调 | 用批改记录训练学徒 |
| 期末考试 | `gold.jsonl` 评测集 | 用人工打的分检验学徒批得准不准 |
| 学徒上岗 | vLLM 本地服务 | 学徒在本地机器上直接干活 |

### 0.3 八步的逻辑关系

```
攒数据 → 导出 → 人工标注 → 测基线 → 训练 → 合并 → 部署 → 测效果 → 压测切换
 (1)     (1)     (2)       (3)      (4)    (5)    (6)     (7)       (8)
```

前三步解决「拿什么教」，中间三步解决「怎么教、教成什么样」，后两步解决「怎么用、用得好不好」。**跳过任何一步，你都无法回答答辩时最关键的问题：微调到底有没有用？**

## 1. 名词速查

| 名词 | 一句话解释 |
|---|---|
| **基座模型（Base Model）** | 训练的起点，比如 Qwen2.5-1.5B-Instruct。我们是在它的基础上改，而不是从零训练 |
| **微调（Fine-tuning）** | 用特定任务的数据，继续训练一个已经会说话的模型，让它在这个任务上更专业 |
| **SFT（监督微调）** | 给模型看「输入 → 标准输出」的成对样本，让它学会模仿。我们的样本是「题目+作答 → 四维分数 JSON」 |
| **LoRA** | 一种省显存的微调方法。不改基座的全部参数，只在旁边加一小组可训练的矩阵，训练完的增量只有几十 MB |
| **rank（秩）** | LoRA 那组小矩阵的「宽度」。越大能学的东西越多，也越占显存。我们用 16 |
| **loss（损失）** | 模型输出和标准答案的差距。训练时它应该越来越小 |
| **过拟合** | 模型把训练数据背下来了，遇到没见过的数据反而变差。验证集的 loss 会先降后升 |
| **合并（Merge）** | 把 LoRA 的增量加回基座，得到一个完整的、独立的模型文件 |
| **量化** | 把模型参数从 16 位压到 4 位，显存约降到三分之一，精度略有损失。AWQ 和 GPTQ 是两种量化方式 |
| **显存（VRAM）** | 显卡自己的内存。模型参数必须放进显存才能快速运行，放不下就跑不起来 |
| **KV cache** | 模型生成文字时缓存的中间结果。上下文越长，占的显存越多 |
| **vLLM** | 一个高效的大模型推理引擎，能把模型包装成 HTTP 服务，吞吐量远高于直接用 transformers 跑 |
| **OpenAI 兼容接口** | 一种通用的 HTTP 格式（`/v1/chat/completions`）。很多服务都支持，代码只要改个地址就能换模型 |
| **ground truth（标准答案）** | 用来打分的「正确答案」。这里是人工打的分 |
| **一致率** | 模型分数和人工分数相差不超过 1 分的比例 |
| **MAE（平均绝对误差）** | 模型分数和人工分数差距的平均值，越小越好 |
| **P50 / P99** | 延迟的分位数。P50 是中位数，P99 是最慢的那 1% 的水平。只看平均值会掩盖尾部的慢请求 |
| **首 token 延迟（TTFT）** | 从发出请求到收到第一个字的时间。决定用户「感觉快不快」 |

## 2. 步骤详解

### 第 0 步：环境检查

**做什么**：确认 Python 环境里有需要的库，显卡能被 PyTorch 识别。

```powershell
conda activate langchain_latest
python -c "import torch; print(torch.cuda.is_available())"
```

**为什么**：这一步看起来多余，但能省下大量时间。微调和部署都依赖 GPU，如果 PyTorch 找不到显卡，后面每一步都会报错，而且报错信息不一定直接指向根因。**先确认底座，再盖楼。**

**你应该看到**：输出 `True`。

**常见问题**：输出 `False` 时，通常是装成了 CPU 版的 PyTorch。去 PyTorch 官网查 CUDA 版本对应的安装命令重装。

---

### 第 1 步：攒数据、导出 SFT 数据集

**做什么**：从数据库里取出所有评分记录，整理成「输入 → 输出」的训练样本，写入 `finetune/data/grader_sft.jsonl`。

**为什么这一步存在**

这个项目最特别的地方是：**训练数据不用另找，系统每次评分都在自动产生它。** 每条评分记录包含：

- 题目和参考答案
- 用户的作答
- 四维分数和理由

把它们拼成一条样本，就是一次完整的「老师批改」示范。积累得越多，学徒学得越好。这个思路叫**数据飞轮**：用户用得越多，数据越多，模型越准。

**为什么要先 `--stats-only`**

先只统计、不导出，看看数据是什么样。你会看到三类信息：

- 有多少条评分记录，其中多少因为缺字段被跳过
- 题目是否已被删除（删除了的题无法还原输入，只能丢弃）
- **总分分布**：这一项最重要。

**分布为什么重要**：如果所有样本都打 3 分左右，模型就学会了「永远打 3 分」，它在训练集上 loss 会很低，但完全没有判断力。这种情况下微调等于白练。你需要的是**高分和低分都有**的数据，让模型知道什么样的回答该得几分。

**`--drop-degenerate` 是什么**

它会剔除四维全是 0 分或全是 5 分的样本。原因和上面一样：这种极端样本信息量低，而且有时是评分出错造成的噪声。

**为什么 prompt 要和线上逐字一致**

这是新手最容易忽略的一点。导出时用的 prompt，直接复用了线上评分时用的 `GRADE_TEMPLATE`。

原因：模型学的是「看到这种格式的输入，就输出这种格式的答案」。如果训练时的输入格式和线上不一样，模型训练得再好，上线后遇到真实输入也会表现失常。这叫**训推不一致**。

**你应该看到**：一份统计表，最后一行是「可用样本」的数量；如果导出成功，`data/grader_sft.jsonl` 里每行是一条 JSON。

---

### 第 2 步：人工标注评测集

**做什么**：从数据库抽取若干条作答，由人按四维 rubric 独立打分，写入 `gold.jsonl` 的 `human_scores` 和 `human_total` 字段。

**为什么这一步存在**

这是**整个微调里唯一无法自动化的一步**，也是最重要的一步。

假设你不做人工标注，只用模型自己的输出来评估模型，会发生什么？模型是在拿自己的答案和自己比，结论没有任何外部依据。答辩时老师问「你怎么证明它打得准」，你只能说「它和它自己一致」，这是无效的。

人工标注给了我们一把**外部的尺子**。它不一定完美（人也会有主观偏差），但它独立于模型，这就足够了。

**为什么是 100 条**

统计上，样本太少时，一致率的波动会很大。50 条里多错 3 条，一致率就掉 6 个百分点，结论不稳定。100 条是一个能让比较有意义的最低门槛。

**标注时的关键原则**

1. **按 rubric 独立打分**：正确性（0.40）、完整性（0.30）、表达（0.15）、术语（0.15），每项 0–5 分。权重决定总分，但每个维度单独打。
2. **不要看模型的分数**：`gold.jsonl` 里有一个 `model_score` 字段。标注时如果先看到它，就会不自觉地向它靠拢，标注就失去了独立性。**先标完，再对照。**
3. **尽量保持标准前后一致**：标注到后面容易疲劳，标准会漂移。可以先标 10 条，回头看看前后打分尺度是否一致。

**新手陷阱**

`--make-template` 会**直接覆盖** `gold.jsonl`（脚本把模板写到 `--gold` 指定的路径，默认就是它）。如果你已经标了一半，再跑一次这个命令，之前的标注会全部丢失。**生成模板只能在第一次做，或者先备份文件。**

---

### 第 3 步：测微调前基线

**做什么**：用当前线上的模型（DeepSeek）跑一遍评测集，把结果存为 `finetune/eval/before.json`。

**为什么这一步存在**

这是**对照组**。科学实验的基本逻辑是：要证明某个东西有效，你必须先知道「没有它」的情况是什么样。

没有 before，after 的数字就没有意义。比如你测出微调后的一致率是 70%，这到底算好还是算差？只有看到「微调前是 40%」，才能说「提升了 30 个百分点」。

**为什么测的是数据库配置的模型，而不是 `.env`**

管理员可能在后台改过模型。`.env` 里写的可能是过期的配置。如果拿它评测，你测的其实是另一个模型，结果就对不上线上的真实情况。**评测的对象必须和线上一致。**

**为什么不做向量检索**

线上评分前会先检索题库里的参考资料。如果评测时也带上检索，before 和 after 的差异就无法区分是「模型变好了」还是「检索变好了」。**评测时只允许模型这一个变量变化。**

---

### 第 4 步：LoRA 训练

**做什么**：用导出的数据集训练一个 LoRA 适配器。这是整个流程里计算量最大、最花时间的一步。

#### 4.1 为什么用 LoRA，而不是全量微调

全量微调会更新模型的**全部参数**。以 1.5B 模型为例，参数有 15 亿个，训练时还要保存优化器状态，显存需求通常是模型本身的 4 倍以上，远超 8GB 的显卡。

LoRA 的思路是：**冻结基座，只训练旁边加的一小组参数。** 可训练参数通常只占总量的百分之一左右，显存需求小得多，而且效果通常接近全量微调。

这就是为什么我们能在笔记本的 8GB 显卡上训练，而不是要租服务器。

#### 4.2 配置文件里几个关键参数

| 参数 | 值 | 含义 |
|---|---|---|
| `model_name_or_path` | Qwen2.5-1.5B-Instruct | 基座模型，训练的起点 |
| `lora_rank` | 16 | 适配器的宽度。够用即可，越大越占显存 |
| `lora_target` | all | 让注意力层和前馈层都参与训练，效果比只训练一部分更好 |
| `cutoff_len` | 4096 | 每条样本最多保留的 token 数。评分 prompt 通常 1500–2500 token，留足余量 |
| `per_device_train_batch_size` | 2 | 一次送进显卡的样本数 |
| `gradient_accumulation_steps` | 8 | 梯度累积 8 次才更新一次参数。显存不够时，用这个换「等效更大的 batch」 |
| 等效 batch | 2 × 8 = 16 | 每次参数更新实际参考的样本数 |
| `learning_rate` | 1e-4 | 每次更新的步子大小。太大会震荡，太小学得慢 |
| `num_train_epochs` | 3 | 把数据完整过 3 遍 |
| `lr_scheduler_type: cosine` | — | 学习率先升后按余弦曲线降，训练后期更稳 |
| `gradient_checkpointing` | true | 用计算时间换显存：不保存中间结果，需要时重新算 |

**新手最常问的一个问题：batch 为什么要这么设计？**

显存只能装下很小的 batch（比如 2），但如果每次只看 2 条样本就更新参数，方向会很抖。梯度累积的做法是：先把 8 次的梯度加起来，再统一更新一次，相当于用 16 条样本的「平均感受」来调整参数。**小显存也能获得稳定的训练。**

#### 4.3 训练时要看什么

训练过程中会不断打印 loss。你需要关注两条曲线：

| 曲线 | 理想走势 | 出现问题时 |
|---|---|---|
| 训练 loss | 持续下降 | 不降：学习率可能太小，或数据有问题 |
| 验证 loss（`eval_loss`） | 下降后趋于平稳 | 先降后升：**过拟合**，应减少 epoch 或降低学习率 |

训练结束后，脚本会把 loss 曲线画成图，存在输出目录里，建议保存下来放进报告。

#### 4.4 显存不够（OOM）怎么办

按优先级依次尝试：

1. 把 `cutoff_len` 降到 2048（代价：长 prompt 会被截断）
2. 把 `per_device_train_batch_size` 改成 1，`gradient_accumulation_steps` 改成 16（等效 batch 不变，显存占用减半）
3. 确认 `gradient_checkpointing` 是开着的

**注意**：这一步要在独立的 `llamafactory` 环境里做。LLaMA-Factory 对 transformers 版本有自己的要求，装进 `langchain_latest` 可能会把你现在的版本降级，导致其他实验失效。**隔离依赖是工程里的基本习惯。**

### 第 5 步：合并权重

**做什么**：把 LoRA 适配器的增量加回基座模型，导出一个完整的、独立的模型目录。

**为什么这一步存在**

LoRA 训练出来的只是「增量」，单独用它没法推理，必须和基座放在一起。但 vLLM 这类推理引擎更适合加载完整的模型目录。把两者合并成一个文件夹，部署时最简单，出问题也最好排查。

**为什么要自己写一个 `merge_lora.yaml`**

`finetune/README.md` 里的写法是把训练配置文件直接传给 `export` 命令。问题是训练配置里**没有指定 adapter 的路径**，导出时脚本不知道要加哪个适配器，会出错。所以合并时必须明确告诉它三件事：

- 基座是谁（`model_name_or_path`）
- 适配器在哪（`adapter_name_or_path`）
- 合并结果存到哪（`export_dir`）

**`export_device: cpu` 是什么意思**

合并只是把数字相加，不需要 GPU。用 CPU 做可以避免显存紧张时的冲突，代价是慢一点，但这一步通常只需要几分钟。

**你应该看到**：`finetune/output/qwen2.5-1.5b-grader-merged/` 目录下出现 `config.json` 和模型权重文件。

---

### 第 6 步：用 vLLM 起本地服务

**做什么**：把合并后的模型启动成一个 HTTP 服务，监听 `127.0.0.1:8001`。

这一步是**部署**的核心。前面的所有工作，最终都要落到「有一个服务在跑，应用能调用它」上。

#### 6.1 为什么要做成服务，而不是直接在代码里调用模型

如果直接在 Python 里加载模型，每次应用重启都要重新加载，而且模型和应用绑死在一起。做成服务之后：

- 模型可以独立运行、独立升级
- 应用只需要知道一个地址，不关心背后是什么模型
- 切换模型时，应用代码一行都不用改

#### 6.2 为什么用 OpenAI 兼容接口

OpenAI 的接口格式已经成为行业通用标准。vLLM 原生支持这种格式，OfferMind 的后端也是按这种格式调用模型的。所以只要把管理后台的 Base URL 从云端地址改成 `http://127.0.0.1:8001/v1`，应用就切换到本地模型了，**代码不用动**。

这也是为什么配置是「热生效」的：改完立即用新模型，不用重启后端。

#### 6.3 为什么用 vLLM，而不是 transformers 直接跑

transformers 是通用的训练和推理库，它一次只处理一个请求，显卡经常在等待。vLLM 做了三件事：

- **连续批处理**：多个请求的计算穿插进行，显卡利用率高
- **PagedAttention**：像操作系统管理内存页一样管理 KV cache，减少显存浪费
- **前缀缓存（`--enable-prefix-caching`）**：评分的 prompt 前半部分（系统指令加评分量表）每次都一样，vLLM 可以把这部分的计算结果缓存起来复用，只算变化的尾部。这能明显降低首字延迟，正是压测里要对比的指标

#### 6.4 为什么必须在 WSL 里做

vLLM 只支持 Linux。Windows 上没有原生版本，所以要在 WSL2（Windows 上的 Linux 子系统）里运行。WSL 能直接调用 Windows 的 NVIDIA 驱动，所以 GPU 仍然可用。

#### 6.5 三个关键参数

| 参数 | 默认值 | 含义 |
|---|---|---|
| `--max-model-len` | 8192 | 服务能处理的最长上下文。越大越占显存，因为 KV cache 随长度增长 |
| `--gpu-memory-utilization` | 0.90 | vLLM 最多占用显卡显存的 90%，剩下留给系统和其他程序。在 8GB 卡上如果启动失败，可降到 0.85 |
| `--dtype` / `--quantization` | fp16 时用 bfloat16 | 精度与量化方式，决定模型占多少显存 |

#### 6.6 精度与量化：为什么有 fp16 和 awq 两种

这是部署里最核心的取舍，也是答辩的重点：

| 方式 | 显存占用 | 速度 | 质量 | 适合场景 |
|---|---|---|---|---|
| FP16（16 位） | 高 | 基线 | 最好 | 显存充足时 |
| AWQ（4 位） | 约为 FP16 的 1/3 | 通常更快 | 损失通常很小 | 显存紧张时 |

**量化的直觉**：模型参数原本每个占 16 位，量化后每个只占 4 位，相当于把高清图压缩成低清图。大部分时候肉眼看不出差别，但细节上会有损失。**「显存–延迟–质量」三角就是要量化这个取舍。**

#### 6.7 这一步的常见错误（文档里写错了的地方）

1. **微调后的模型不要加 `awq` 参数**。`awq` 会告诉 vLLM「这是量化模型」，而你的模型是 FP16 的，会启动失败。正确写法：

   ```bash
   MODEL=finetune/output/qwen2.5-1.5b-grader-merged bash deploy/vllm/serve.sh fp16
   ```

2. **AWQ 要用量化版本的模型**。`serve.sh` 的 `awq` 分支默认加载的是未量化的 7B 模型，两者不匹配。要跑 AWQ，必须指定量化版本：

   ```bash
   MODEL=Qwen/Qwen2.5-7B-Instruct-AWQ bash deploy/vllm/serve.sh awq
   ```

3. **served model name 是什么**：`serve.sh` 会把模型目录的名字作为对外的模型名。比如目录叫 `qwen2.5-1.5b-grader-merged`，调用时 `model` 字段就要写这个名字，写错会得到「模型不存在」的错误。

4. **用 127.0.0.1，不要用 localhost**：Windows 上 `localhost` 有时会先尝试 IPv6 地址，连接失败后要等很久才回退，表现为「卡住二十多秒」。

**验证服务是否起来**：

```powershell
curl http://127.0.0.1:8001/v1/models
```

返回的 JSON 里能看到你的模型名，说明服务正常。

---

### 第 7 步：测微调后、出对比表

**做什么**：用同一份评测集，让微调后的本地模型打分，然后把 before 和 after 放在一起比较。

**为什么这一步存在**

这是**验证**。训练完不等于有效，必须用同一把尺子量一遍才知道。

**为什么 `--model` 必须和服务端的模型名一致**

评测脚本会把请求发到你指定的地址。模型名不一致时，服务会拒绝请求。这一步是最常见的失败点之一。

#### 7.1 指标解释

| 指标 | 怎么算 | 为什么这样定义 |
|---|---|---|
| 一致率 | 模型分与人工分相差 ≤1 分的比例 | 评分是主观量表，要求每个维度完全相等太苛刻，允许 1 分误差更合理 |
| 完全相同 | 相差为 0 的比例 | 衡量严格一致的程度 |
| MAE | 每一项误差绝对值的平均 | 看整体偏移的幅度。能看出模型是普遍偏高还是偏低 |

**看结果时的思路**：

- 一致率提升、MAE 下降：微调有效
- 一致率提升、MAE 没降：可能是边界样本变好了，但极端误差还在
- 两者都没改善：**如实写下来**。微调没效果也是有价值的结论，它说明数据或训练配置可能有问题，这本身就是可以讨论的内容

**不要为了好看而挑样本。** 评测集一旦定下，就用它完整地跑所有模型。

#### 7.2 对比表怎么读

`--compare` 会输出每个维度的 before → after 变化，并标注是否改善。你要的是**整体趋势**，而不是某一个维度的单点数字。

---

### 第 8 步：压测与切换到线上

**做什么**：用固定的请求负载测量本地服务和云端的性能，然后决定是否切换。

**为什么这一步存在**

「模型准」是一个维度，「服务快」又是另一个维度。部署的价值最终要用这两者一起衡量。一个准确率高但慢得不能用的模型，在线上是没有意义的。

#### 8.1 压测指标

| 指标 | 含义 | 为什么重要 |
|---|---|---|
| 首 token 延迟 | 发出请求到收到第一个字 | 决定用户体感，流式输出时尤其明显 |
| 总延迟 P50 | 一半请求比这个快 | 典型体验 |
| 总延迟 P99 | 99% 的请求比这个快 | 最慢的那一小部分，决定最坏情况 |
| 吞吐（req/s） | 每秒能完成多少请求 | 服务的容量上限 |

**为什么要看 P99 而不是只看平均值**：平均值会掩盖少数极慢的请求。一个平均 2 秒的服务，可能有 1% 的请求要 20 秒，用户会觉得它「时好时坏」。

#### 8.2 压测为什么要固定 prompt 长度

prompt 越长，计算越多，延迟越高。如果两次压测的输入长度不同，比出来的数字没有可比性。所以 `bench_llm.py` 用 `--prompt-chars` 固定了输入长度。

#### 8.3 切换到线上

在管理后台「模型配置」里：

- Base URL 改成 `http://127.0.0.1:8001/v1`
- 模型名改成 `qwen2.5-1.5b-grader-merged`

改完立即生效，不用重启。**但切换前要先想清楚：** 本地模型的质量已经在第 7 步验证过了，性能在第 8 步验证过了，两者都满足你的需求再切。如果本地服务停了，评分会失败，所以要保留切回云端的能力（配置网关的回退规则可以自动切换）。

## 3. 答辩时常见的问题，以及你该怎么答

| 问题 | 回答的依据 |
|---|---|
| 你的微调有没有效果？ | 第 7 步的 before / after 对比表，看一致率和 MAE 的变化 |
| 评测的标准答案哪来的？ | 第 2 步的人工标注，说明标注人数、标注原则、是否独立于模型 |
| 为什么用 1.5B 而不是 7B？ | 显存限制（8GB）；LoRA 让小显存训练成为可能 |
| 为什么用 LoRA？ | 省显存，训练成本低，效果接近全量微调 |
| 本地部署比云端好在哪？ | 第 8 步的延迟和成本数据；同时要诚实说明质量的差距 |
| 量化会损失多少质量？ | 第 7 步用同一份评测集量化前后的指标，不要只凭感觉 |
| 如果本地服务挂了怎么办？ | 网关的回退规则，自动切到云端 |

**答辩的核心原则：** 每个结论都要能指向一个具体的数字或一份具体的文件。说「效果不错」不如说「一致率从 X% 提升到 Y%，MAE 从 A 降到 B，评测集共 N 条，由 M 人标注」。

## 4. 常见错误速查

| 现象 | 大概率原因 | 怎么查 |
|---|---|---|
| `torch.cuda.is_available()` 为 False | 装了 CPU 版 PyTorch | 重装对应 CUDA 版本的 PyTorch |
| 导出后样本数很少 | 大量评分记录缺字段或题目已删 | 看 `--stats-only` 的各项跳过计数 |
| 训练 OOM | 显存不够 | 降低 `cutoff_len`，调整 batch 与梯度累积 |
| `eval_loss` 先降后升 | 过拟合 | 减少 epoch，降低学习率 |
| 合并时报错找不到 adapter | 合并配置没指定 `adapter_name_or_path` | 使用本文第 5 步的 `merge_lora.yaml` |
| vLLM 启动失败，提示量化相关错误 | 量化参数与模型不匹配 | 确认 fp16 模型不加 `awq`，awq 要用量化版本 |
| 服务起来了，调用返回「模型不存在」 | `--model` 名字与 served name 不一致 | `curl .../v1/models` 查看真实名字 |
| 连接本地服务卡住约 20 秒 | Windows 的 localhost 解析问题 | 改用 `127.0.0.1` |
| 之前的人工标注不见了 | 重跑了 `--make-template` 覆盖了 gold.jsonl | 以后先备份再生成模板 |
