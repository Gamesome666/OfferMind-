## 坑 1 · DeepSeek 的 function calling 不保证 `arguments` 是合法 JSON

### 现象

用工具调用（function calling）模式做结构化输出时，**约三成概率**拿到 `None`，上层报错：

```
'NoneType' object has no attribute 'model_dump'
```

报告类长文本任务（面试报告、训练报告、简历诊断）尤其容易触发。

### 根因

工具调用模式下，模型把参数写在 `arguments` 字符串里，而这个字符串**不保证是合法 JSON**。

模型只要在某个字符串值里写了**未转义的引号**，整段 JSON 就废掉：

```
"采用"总分总"结构作答"        ← 内层引号没转义
```

langchain 解析工具调用失败后返回 `None`，于是 `.model_dump()` 崩掉。

**关键认识：这不是偶发抖动，是长文本生成的固有风险。** 文本越长、引号越多，出现未转义引号的概率越高。「约三成」这个数字是在本项目实际运行中观察到的。

### 解法

改用 `response_format={"type": "json_object"}`：

```python
class JsonSchemaLLM:
    def __init__(self, llm: ChatOpenAI, schema) -> None:
        self._llm = llm.bind(response_format={"type": "json_object"})
        self._schema = schema
        self._instructions = PydanticOutputParser(
            pydantic_object=schema
        ).get_format_instructions()

    def invoke(self, messages):
        result = self._llm.invoke([*messages, HumanMessage(content=self._instructions)])
        return self._schema.model_validate_json(result.content)
```

**为什么这能解决**：`json_object` 不是「请求模型输出 JSON」，而是**服务端约束解码** —— 在生成过程中就限制 token 选择，保证输出必然是合法 JSON。这是解码层面的保证，不是提示词层面的请求。

**代价**：`json_object` 要求 prompt 里出现 "json" 字样。所以要把 Pydantic 的格式说明作为**最后一条 `HumanMessage` 追加**进去（说明文本里天然含 "json" 字样）。

**一个容易踩的细节**：`bind()` 是**累积语义**，所以 `bind(response_format=...)` 与后续的 `client.bind(extra_headers=headers)`（会话头）可以叠加，互不干扰。同样 `LiteLLMChat.bind` 也是累积语义。

### 防回归

- 所有需要固定结构的 LLM 调用一律走 `JsonSchemaLLM`，不走 `bind_tools`
- 面试 HR 对话**刻意不走结构化输出**（它需要的是自由文本流），这是唯一例外
- 若将来要引入工具调用（如管理端智能助手），应**手写 JSON ReAct** 而不是用 `bind_tools`：让模型每轮输出 `{thinking, tool, arguments, reply}`，服务端解析后执行

## 坑 2 · 并发构造 HuggingFace 模型会得到半初始化实例

> 这是本项目最严重的一个 bug —— 因为它一旦发生，**坏实例会被缓存，之后永久生效**。

### 现象

服务启动后，所有涉及 embedding 或 rerank 的请求都报：

```
Cannot copy out of meta tensor; no data!
```

而且**重启后必定复现**，不像偶发故障。

### 根因

启动时的**预热线程**与**第一个真实请求**会同时进入 `_load()`：

```python
# 有问题的写法
def get_embeddings():
    global _instance
    if _instance is None:
        _instance = BgeEmbeddings()      # 两个线程可能同时执行这一行
    return _instance
```

两个线程同时构造同一个 HF 模型 → 得到**半初始化实例**（权重还在 meta device 上没搬过来）→ 所有调用报 `Cannot copy out of meta tensor`。

**为什么「永久生效」**：坏实例被赋给了模块级 `_instance`，之后所有调用都拿到它，所以不会自愈。

### 解法：两层锁

**第一层：模块级单例锁**

```python
_singleton_lock = threading.Lock()
_instance: BgeEmbeddings | None = None

def get_embeddings() -> BgeEmbeddings:
    global _instance
    if _instance is None:
        with _singleton_lock:
            if _instance is None:            # 双重检查
                _instance = BgeEmbeddings()
    return _instance
```

**第二层：类内加载锁**

```python
class BgeEmbeddings:
    def __init__(self):
        self._lock = threading.Lock()
        self._model = None

    def _load(self):
        if self._model is None:
            with self._lock:
                if self._model is None:      # 双重检查
                    from sentence_transformers import SentenceTransformer
                    self._model = SentenceTransformer(self.model_name)
        return self._model
```

`bge-reranker`（`reranker.py`）与 BM25 索引（`bm25.py`）采用完全同构的写法。

### 一个刻意的选择：不用 `lru_cache`

**`lru_cache` 是线程安全的（内部有锁），但它不加构造锁** —— 两个线程可能各自构造一份，虽然只有一份会进缓存，但**两份模型都会占用显存**。

在 2GB+ 权重的模型上，「多构造一份」意味着多占 2GB 显存。所以这里刻意用显式锁 + 全局变量，而不是 `lru_cache`。

**注意对比**：LLM 客户端（`llm.py`）反而**用了** `lru_cache`。因为 `ChatOpenAI` 客户端的构造是廉价的（只是配置对象），多构造一份无害；而 HF 模型的构造是昂贵的。**同一个项目里两种选择，取决于构造成本。**

### 防回归

- 任何新引入的本地模型（如未来的 Laya 决策引擎）必须复用同一套「双重检查锁 + 模块级单例」模式
- 预热函数（`_warm_up_models`）与真实请求路径**共用同一个单例入口**，这是复现该 bug 的前提条件，也是防止它再次发生的关键

## 坑 3 · Next.js 的 rewrites 会缓冲整个 SSE 响应

### 现象

前端通过 `next.config.mjs` 的 `rewrites` 把 `/api/*` 代理到后端。结果是：

- 执行面板在请求期间**一动不动**
- 请求结束后，**所有事件一次性全部出现**
- 面试的 HR 回复从「逐字流式」退化成「整段一次性出现」

### 根因

Next.js 的 rewrite 是一个**服务端代理**。它收到后端的 `text/event-stream` 响应后，会**先把整个响应体读完**再转发给浏览器 —— 也就是对 SSE 做了缓冲。

而 SSE 的全部价值建立在「产生一条推一条」上。被缓冲之后，它与普通 JSON 响应没有区别。

### 解法

前端**直连**后端，跨域由后端 CORSMiddleware 放行：

```ts
// frontend/lib/api.ts
const API_BASE = process.env.NEXT_PUBLIC_API_BASE ?? "http://127.0.0.1:8000";
```

```python
# backend/app/main.py
app.add_middleware(
    CORSMiddleware,
    allow_origin_regex=r"http://(localhost|127\.0\.0\.1)(:\d+)?",
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

### 顺带解决的一个问题：为什么用正则而不是端口列表

**Next 开发服务器在 3000 被占用时会自动顺延到 3001 / 3002。** 如果用 `allow_origins=["http://localhost:3000"]` 这样的固定列表，新端口上的前端**每个请求的 CORS 预检都返回 400「Disallowed CORS origin」**。

这个错误的迷惑性在于：它看起来像后端故障，实际上只是端口变了。

**约束**：`allow_credentials=True` 时不能用 `allow_origins=["*"]` 通配。正则方案同时满足「允许任意本地端口」与「不使用通配符」两个要求。

### 防回归

- `next.config.mjs` 保留为空配置，并**在注释里写明为什么不用 rewrites** —— 防止后来者「顺手优化一下」把它加回来
- 后端 SSE 响应统一带 `X-Accel-Buffering: no`，让 nginx 等反向代理也不缓冲
- 生产环境部署时，CORS 正则必须收紧成真实前端域名（代码注释已标注）

## 坑 4 · SM-2 的毕业规则：答对一次就移出错题本会让复习计划永远不触发

### 现象

错题本的「待复习」标签页**永远是空的** —— 即使刚刚答错了一道题并生成了复习计划。

### 根因

**待复习队列的查询条件是 `is_wrong = True AND review_due_at <= now`。**

如果毕业规则是「复习答对一次就置 `is_wrong = False`」，那么逻辑推演是：

```
用户答错 → is_wrong=True，SM-2 排期：明天、6 天后、15 天后、37 天后……
       ↓
第一次复习答对 → is_wrong=False，记录立刻退出待复习队列
       ↓
SM-2 排出的后续复习节点（6 天、15 天、37 天……）永远不会被触发
       ↓
间隔重复退化成「复习一次就结束」，SM-2 算法等于没实现
```

### 解法：连续答对 N 次才毕业

```python
MASTERED_REVIEWS = 2   # 连续答对多少次算「已掌握」

if reps >= MASTERED_REVIEWS:
    answer.is_wrong = False
```

**为什么是「连续」答对**：SM-2 在 `quality < 3` 时会**把 repetition 清零**，所以 `review_count` 天然等于「连续答对次数」。这个语义不需要额外字段来记录。

**代码注释（防回归的关键）**：

> 注意不要「答对一次就移出错题本」—— 那会让刚排的复习计划永远不会触发（待复习队列是按 `is_wrong` 过滤的）。改为**连续答对 MASTERED_REVIEWS 次**才毕业，这样中间的复习节点都能正常到期。

### 防回归

- `review_count` 的语义（**连续答对次数**，不是复习总次数）写进了字段注释
- 修改 SM-2 相关逻辑时，必须同时验证「待复习队列能取到数据」这条路径
- 这个坑的本质是**两个机制的隐式耦合**：毕业条件与查询过滤条件共享 `is_wrong` 字段。任何修改其中一方的行为都要检查另一方

## 坑 5 · `Base.metadata.create_all` 不给已有表加列

### 现象

新增了 `users.is_admin` 字段、给 `answers` 表加了四个 SM-2 字段后，在**已建表的数据库**上跑 `python init_db.py`，然后查询时报：

```
column users.is_admin does not exist
```

### 根因

**`Base.metadata.create_all` 只建缺失的表，不会给已有表加列。** 这是 SQLAlchemy 的明确行为（不是 bug）。

因为它的语义是「确保这些表存在」，而不是「确保表结构与模型一致」。结构同步需要迁移工具。

### 解法：手写幂等 DDL 迁移列表

`backend/init_db.py` 里维护三段列表：

```python
_COLUMN_MIGRATIONS = (
    ("users", "is_admin", "BOOLEAN NOT NULL DEFAULT FALSE"),
    ("interview_sessions", "status", "VARCHAR(16) NOT NULL DEFAULT 'active'"),
    # 错题本 / 间隔重复（SM-2）的调度状态
    ("answers", "review_due_at", "TIMESTAMP"),
    ("answers", "review_interval_days", "INTEGER NOT NULL DEFAULT 0"),
    ("answers", "review_ease", "DOUBLE PRECISION NOT NULL DEFAULT 2.5"),
    ("answers", "review_count", "INTEGER NOT NULL DEFAULT 0"),
)

_INDEX_MIGRATIONS = (("ix_answers_review_due_at", "answers", "review_due_at"),)

_COLUMN_RELAX = (("interview_sessions", "rounds_json"),)
```

| 类型 | 执行语句 | 幂等保证 |
|---|---|---|
| 加列 | `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` | ✅ |
| 加索引 | `CREATE INDEX IF NOT EXISTS` | ✅ |
| 放宽约束 | `ALTER TABLE ... ALTER COLUMN ... DROP NOT NULL` | ✅（重复执行无副作用） |

**全部幂等，可重复执行**，输出永远是「数据库表已创建 / 更新」。

### 附带的取舍：不删列

`interview_sessions.rounds_json` 被 `interview_messages` 表取代后，模型里已不再声明它。但**列仍然存在于已建表的数据库里**，且原本是 `NOT NULL`。

如果不放开约束，新会话插入时不会带这个字段，就会报 `NotNullViolation`。

处理方式是**只去掉 NOT NULL，不删列不删数据**：

> rounds_json 已被 interview_messages 取代，模型里不再声明它。这张表原本建的是 NOT NULL，不放开的话新会话插入会报 NotNullViolation。只去掉 NOT NULL、不删列不删数据。

**理由**：删列是不可逆操作，而留着一个空列几乎没有成本。

### 为什么不用 Alembic

| 方案 | 本项目情况 |
|---|---|
| Alembic | 需要维护迁移链、版本目录；单一开发环境不需要多人协作的迁移管理 |
| 手写幂等 DDL | 零依赖、一眼看懂做了什么、可重复执行 |

结构简单时，手写迁移的认知成本低于引入迁移框架。

### 防回归

- **新增字段时必须同时改两处**：模型类 + `init_db.py` 的 `_COLUMN_MIGRATIONS`
- 改现有字段的约束（如从 NOT NULL 改为可空）要写进 `_COLUMN_RELAX`
- 这条约定已写在 `CLAUDE.md` 里，属于项目级规范

## 坑 6 · 评分落库必须带 `question_id`，缺失时宁可不记录

### 现象

评分结果有时会落库，有时不会。更危险的情况是：如果把评分挂到了错误的题目上，错题本会显示「这道题的作答是另一道题的答案」。

### 根因

评分是**独立的一次请求**（`POST /training/grade/stream`），它只知道题目文本与作答文本，**不知道用户是在做哪一道题**。如果出题结果里没有把 `question_id` 传给前端、前端也没带回来，服务端就无从判断这条评分应该挂到哪道题上。

### 解法：硬性要求 + 优雅降级

**出题结果里回传 `question_id`** → **前端评分时带回** → **服务端检查**：

```python
if question_id is None:
    # 不落库，但评分结果照常返回
    ...
else:
    answer = await answer_repo.create(db, user_id, question_id, ...)
    yield {"type": "已记录", "payload": {"answer_id": answer.id, "is_wrong": answer.is_wrong}}
```

**原则：宁可不记录，也不要记录到错的题上。**

这个取舍的理由：错题本与微调数据集都依赖 `answers` 表的**题目关联正确性**。一条挂错题的记录会污染错题本（复习一道没做错的题）与训练数据（题目与作答不匹配的样本会教坏模型）。相比之下「漏记一条」只是少了一条数据。

### 顺带的一个不一致（已知边界）

| 端点 | 落库 | 要求 `question_id` |
|---|---|---|
| `POST /training/grade`（非流式） | **否** | 无 |
| `POST /training/grade/stream`（流式） | **是** | 必须 |

非流式版本定位是「给 curl / 测试用」，因此没接数据库依赖。但同名两个端点行为不同，容易踩坑。

### 防回归

- `question_id` 是出题结果、评分请求、落库三处的必传字段，**改动其中任何一处都要检查链路**
- 落库前校验字段完整性，缺失时不落库并**明确日志提示**（而不是静默跳过）

## 坑 7 · 第一个管理员的鸡生蛋问题

### 现象

管理后台需要管理员权限才能进。那么**第一个管理员从哪来**？

### 根因

典型的引导问题（bootstrap problem）：权限系统需要一个已授权的用户来授权第一个用户。

### 解法：命令行工具

```bash
python promote_admin.py user@example.com
```

```python
"""第一个管理员必须从命令行给 —— 否则就成「鸡生蛋」了。重复执行安全。"""
```

实现很简单：按 email 查用户，`user_repo.update(db, user.id, is_admin=True)`，打印「已将 {email} 设为管理员」。用户不存在时提示「找不到用户：{email}」，参数数量不对时打印用法并退出。

**为什么会需要这个工具，而不是在首次启动时自动创建一个默认管理员**：自动创建默认管理员意味着一个**已知的默认凭据**（如 `admin/admin`），这是典型的安全漏洞。命令行工具把「谁成为第一个管理员」的决定权留给了有服务器访问权限的人。

### 附带的自我保护规则

管理后台还有两条**后端硬拦截**（返回 400）：

| 操作 | 结果 |
|---|---|
| 取消自己的管理员权限 | **400 拒绝** |
| 删除自己 | **400 拒绝** |

理由：前者会让系统瞬间失去最后一个管理员（如果只有一个），后者会把你锁在门外。这两条都无法通过前端绕过（后端拦截）。

### 防回归

- `promote_admin.py` 设计为**幂等**（重复执行安全），可以在任何时候重跑
- 管理员相关的自我操作校验必须在**后端**，不能只靠前端隐藏按钮

## 坑 8 · Windows 下 `localhost` 解析到 IPv6 导致静默超时

### 现象

在 Windows 上连接 Docker 里跑的 PostgreSQL / Qdrant，会**静默卡住 20 秒以上**才成功（或超时失败）。日志里没有明显错误。

### 根因

**Windows 下 `localhost` 会优先解析到 IPv6 的 `::1`，而 Docker Desktop 只把端口映射到了 IPv4。**

连接 `::1` 时没有服务监听，于是 TCP 连接要等到超时才会回退到 IPv4。整个过程是**静默的** —— 没有报错，只是慢。

### 解法：全项目统一用 `127.0.0.1`

```python
# 统一用 127.0.0.1：Windows 下 localhost 会先解析到 IPv6 ::1，而 Docker 端口只映射了 IPv4，
# 连 ::1 会静默超时 20 秒以上才回退到 IPv4。
database_url: str = "postgresql+asyncpg://offermind:offermind@127.0.0.1:5432/offermind"
```

这条约定覆盖：数据库连接串、Qdrant URL、MinIO endpoint、前端 `NEXT_PUBLIC_API_BASE`、`.env.example` 的注释说明。

### 同类问题：HuggingFace 的冷启动超时

**现象**：每次冷启动应用都要多等 20–30 秒。

**根因**：`huggingface_hub` 会向 `huggingface.co` 发 HEAD 请求检查模型是否有更新。国内直连会超时重试 5 次，每次等待若干秒。

**解法**：在包级 `__init__.py` 里全局设死离线模式：

```python
# app/rag/__init__.py
os.environ.setdefault("HF_HUB_OFFLINE", "1")
os.environ.setdefault("TRANSFORMERS_OFFLINE", "1")
```

**用 `setdefault` 而不是直接赋值**，是为了给「显式想联网」的场景留出覆盖空间。

**对比这两个坑的共性**：都是**网络层的静默等待** —— 不报错，只是慢。这类问题的排查成本远高于报错型问题，因为「慢」作为一个现象几乎没有指向性。

### 防回归

- 项目内所有连接串一律写 `127.0.0.1`，`.env.example` 顶部有醒目注释
- 新增任何外部服务连接时都要检查这一点

## 坑 9 · 训推不一致：导出的训练 prompt 必须与线上逐字一致

### 现象

（这是一个**被提前防住的坑**，不是实际发生的故障 —— 但它是微调环节最容易犯且后果最严重的错误，因此记录在此。）

如果训练数据里的 prompt 与线上推理时喂的 prompt 有差异（哪怕只差一个标点、一个换行、一个空格的顺序），模型就是在为**另一个任务**做优化。结果是微调效果大打折扣甚至完全无效，而且**从 loss 曲线上完全看不出来** —— loss 在降，模型在学，只是学的东西在线用不上。

### 根因

训练数据导出脚本与线上推理代码，通常位于不同模块，很容易出现「复制一份 prompt 文本」的做法。一旦线上改了 prompt，导出的数据集不会跟着变。

### 解法：用 `import` 而不是复制

```python
# scripts/export_sft_dataset.py
from app.agent import prompts

def build_grade_prompt(question: str, reference: str, answer: str) -> str:
    """构造与线上完全一致的评分 prompt。"""
    return prompts.GRADE_TEMPLATE.format(
        question=question,
        reference=reference or "无",
        answer=answer,
        GRADE_RUBRIC=prompts.GRADE_RUBRIC,
    )
```

`system` 字段同样复用：

```python
def to_alpaca(prompt: str, score: dict) -> dict:
    return {
        "system": prompts.SYSTEM_PROMPT,     # ← 复用线上
        "instruction": prompt,
        "input": "",
        "output": json.dumps(score, ensure_ascii=False),
    }
```

**关键点：不是「记得同步」，而是让「不同步」在工程上不可能发生。** 离线脚本直接引用线上模块，prompt 只有一份。

**这正是 `app/agent/` 与 `app/rag/` 被设计为独立包、不依赖 Web 层的原因之一** —— 离线脚本可以只 import 这两个包，而不需要拉起整个 FastAPI 应用。

### 代价

导出脚本因此依赖应用代码，不能脱离项目独立运行。这是一个值得的耦合。

### 一个相关的一致性细节

评测脚本（`eval_grader.py`）同样复用 `prompts.GRADE_TEMPLATE` + `prompts.SYSTEM_PROMPT`，且走 `get_structured_llm(GradeOutput, ...)` —— 即**评测与线上用的是同一套结构化输出封装**。这样「微调后评测」测的确实是「线上会怎么表现」。

### 防回归

- prompt 只在 `app/agent/prompts.py` 定义一份，**任何地方都不允许复制文本**
- 导出脚本与评测脚本必须通过 `import` 引用
- 若将来把 prompt 搬到数据库（管理端 prompt 管理，见演进规划），需要保证导出脚本也从同一来源读取

## 10 · 其他值得记录的工程细节

### 10.1 非流式路径统一包线程池

```python
await asyncio.to_thread(_invoke, graph.xxx, {...}, runtime)
```

**原因**：`graph.invoke()` 与本地 embedding / rerank 都是**同步阻塞调用**。直接在协程里 await 会把事件循环卡住，导致**其他所有请求都无法响应**。

**注意**：`asyncio.to_thread` 内部线程**无法被真正中断**。所以 shutdown 时 `warmup_task.cancel()` 只是取消了 asyncio task，线程仍在后台跑完。这是 Python 的固有限制，对预热这种一次性任务影响可接受。

### 10.2 预热任务必须用变量持有

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    # 用变量持有 task，避免被垃圾回收导致预热中途夭折
    warmup_task = asyncio.create_task(asyncio.to_thread(_warm_up_models))
    try:
        yield
    finally:
        warmup_task.cancel()
```

**为什么**：`asyncio.create_task` 返回的 Task 如果没有任何强引用，可能被 GC 回收，导致预热任务中途消失。这是一个很隐蔽的坑 —— 表现是「预热有时成功有时没跑」，看起来像随机故障。

### 10.3 预热跑真实推理，不只是加载权重

```python
warmups = (
    ("BGE-M3", lambda: get_embeddings().embed_query("模型预热")),
    ("bge-reranker-v2-m3", lambda: get_reranker().rerank("模型预热", ["模型预热的占位文档"])),
)
```

**原因**：GPU 上的**首次推理**有额外的初始化开销（CUDA kernel 编译、显存分配等）。只加载权重不跑推理，这份开销会推迟到第一个真实用户请求上。

预热失败只记日志、不影响启动 —— 因为首次真实调用时会再加载一次。

### 10.4 `expire_on_commit=False` 的取舍

```python
async_session = async_sessionmaker(engine, class_=AsyncSession, expire_on_commit=False)
```

**默认行为**（`expire_on_commit=True`）是 commit 后让对象属性过期，下次访问属性会触发一次新的 SELECT 来刷新。在 async 环境下，这个隐式的数据库访问非常容易出错（在 session 关闭后访问属性会抛异常）。

设为 `False` 后，commit 后对象属性仍可直接读取，所以 repository 里大量「`commit()` 后直接返回对象」的写法才能工作。

**代价**：对象可能与数据库实际状态不一致（如果 commit 后有其他事务改了同一行）。在本项目的使用模式下（写入后立即返回给调用方）不构成问题。

### 10.5 `llm_api_key` 必须在 LLM 客户端的缓存键里

```python
@lru_cache(maxsize=64)
def _get_llm_cached(model: str, base_url: str, api_key: str, temperature: float): ...
```

**为什么密钥要进缓存键**：如果不在键里，「只换了密钥」不会触发新客户端的构造，仍会用旧密钥请求 —— 表现为「在后台改了密钥但不生效」。

**为什么会话头不进缓存键**：

```python
# 会话头不进缓存键：它是每次请求变的，进了缓存键会让客户端缓存彻底失效
return client.bind(extra_headers=headers) if session_id else client
```

会话 id 是**每次请求新生成**的，如果进缓存键，缓存永远不命中（每次都构造新客户端，丢失连接池复用）。解法是用 `bind` 按调用附加。

**这两个决策的方向相反，取决于「这个参数是否频繁变化」**：密钥变得少（要进键，否则改不生效），会话头变得多（不能进键，否则缓存全失效）。

### 10.6 检索事件的失效时机放在「Qdrant 写完」之后

```python
def _invalidate_sparse_index() -> None:
    """题库向量有变更时让 BM25 索引失效。

    放在这里而不是 repository：BM25 的语料就是从 Qdrant 拉的，所以「Qdrant 写完」
    才是失效的正确时机。放在 PG 写入处会早一步 —— 索引重建时还看不到新题。
    """
```

**这个细节很容易做错**：直觉上「PG 写完了就该让索引失效」，但 BM25 的语料来源是 Qdrant 而不是 PG。如果在 PG 写入后就失效，下一次检索会重建索引，而此时 Qdrant 还没写完 —— 新题不在索引里，索引就被「提前重建成了旧内容」。

**通用教训**：**失效信号要绑定在「数据源真正写完」的那一刻**，而不是「逻辑上的写操作开始」那一刻。缓存失效的时机错误表现为「偶然失效」，极难复现。

### 10.7 一处真实的代码缺陷：`llm_options` 重复定义

`app/api/v1/admin.py` 中 `GET /admin/llm/options` 被定义了两次（第 229 行与第 297 行）。FastAPI 按装饰顺序注册，**后注册者覆盖前者**，所以第一个函数是永不执行的死代码。

**影响**：路由装饰器总数 48 个，实际有效端点 47 个；读者会困惑「改这里为什么没效果」。

**修正方式**：删除第一处定义。这类问题无法通过静态检查发现（两个函数语法都合法），只能靠人工审查或端点数量核对。

## 11. 踩坑记录小结

| # | 坑 | 本质 | 通用教训 |
|---|---|---|---|
| 1 | function calling 的 JSON 不合法 | 误解了模型的输出保证级别 | 能从解码层保证的，不要靠提示词请求 |
| 2 | 并发构造 HF 模型 | 单例的并发安全 | 昂贵对象必须加构造锁；`lru_cache` 不解决构造竞争 |
| 3 | Next rewrites 缓冲 SSE | 中间层不透明的缓冲行为 | 流式链路要逐层确认「有没有人在缓冲」 |
| 4 | SM-2 毕业规则 | 两个机制共享字段的隐式耦合 | 改共享字段的行为要检查所有消费方 |
| 5 | `create_all` 不加列 | 对 ORM 工具的语义误解 | 工具的确切语义要查文档，不要凭名字推断 |
| 6 | 评分挂错题 | 跨请求的状态传递 | 数据关联正确性优先于「多记一条」 |
| 7 | 首个管理员的引导 | 权限系统的自举 | 不要为便利引入默认凭据 |
| 8 | IPv6 静默超时 / HF 冷启动 | 网络层的静默等待 | 「慢」比「报错」难查得多 |
| 9 | 训推不一致 | 两处代码需要保持一致 | 用引用消灭「需要保持同步」这件事 |
| 10.1–10.7 | 若干 | 异步/生命周期/缓存时机/代码卫生 | 见各条 |

**这些坑的共同特征**：它们**都不是设计阶段能想到的**。第 1、3、8 条必须先跑起来才会暴露；第 2 条只在并发时出现；第 4 条是改了代码之后才发现的回归；第 5 条是对工具语义的误解。这正是「工程实践」这一篇的价值所在 —— 它记录的是**做过才知道的事**。
