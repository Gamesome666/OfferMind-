## 1. 选题背景

### 1.1 求职侧的三个真实痛点

计算机方向求职者的准备过程，通常由三件事构成，而这三件事目前都有明显缺口：

| 环节 | 求职者的实际做法 | 缺口 |
|---|---|---|
| **刷题** | 在题库平台按标签刷，看别人的题解 | 平台只给标准答案，**不评价自己的作答**。写了什么、差在哪、该补哪一块，全靠自己猜 |
| **简历** | 用在线简历工具排版，或套模板 | 工具只管**排版**，不管**内容质量**。简历和具体岗位 JD 的匹配度没人算 |
| **面试** | 找同学互面、看面经 | 真实模拟成本极高（要找人对练），且面完**没有结构化反馈** |

### 1.2 现有 AI 方案为什么不够用

直接用通用大模型（ChatGPT 类）能补上一部分，但暴露出四类结构性问题：

| 问题 | 具体表现 |
|---|---|
| **黑盒** | 用户只看到一个答案，看不到模型检索了什么、调用过什么工具、依据是什么 |
| **无参照** | 模型的回答是通用知识，不是「这个岗位、这个难度、这个方向」的参考答案 |
| **评分不可解释** | 如果说「你这题 7 分」，用户无法知道扣在哪、怎么改 |
| **无追踪** | 每次对话都是独立的一次性交互，没有跨次的能力画像、没有历史记录、没有复习排期 |

### 1.3 本项目的切入点

**OfferMind 不做「更好的通用问答」，而是做「一次完整的训练闭环」**：

```
        定向刷题 ──→ 作答评测 ──→ 错题沉淀 ──→ 间隔复习
           ↑                                        │
           └────────── 能力画像持续更新 ←────────────┘
                       ↑
        简历诊断 ──→ 模拟面试 ──→ 面试报告 ──→ 画像
```

四条业务闭环（刷题 / 简历 / 面试 / 报告）共享一份**长期能力画像**，全程由**可观测的 Agent 执行面板**贯穿 —— 用户能实时看到 Agent 在检索什么、调用什么模型、每一步花了多久。

## 2. 项目定位

> **OfferMind —— 可观测 Agentic RAG 驱动的 AI 求职面试训练平台**

三个关键词的含义：

| 关键词 | 含义 | 为什么重要 |
|---|---|---|
| **Agentic** | 由 Agent 自主编排「检索 → 生成 → 校验 → 重试」的决策流程，而不是一次 LLM 调用完事 | 出题要查重、评分要参照题库、面试要按简历深挖 —— 都是多步决策 |
| **RAG** | 回答前先从知识库检索真实参照（题库 / 面经 / 简历），用检索结果约束生成 | 让答案有据可依，而不是模型凭记忆编 |
| **可观测** | Agent 的每一步（模型调用 / 向量检索 / 工具调用）都以结构化事件实时推给前端展示 | 产品的差异化卖点，也是调试与成本治理的基础 |

### 2.1 与已有方案的对比

| 方案类型 | 代表 | 局限 | 本项目优势 |
|---|---|---|---|
| 通用刷题平台 | 题库类网站 | 只有题和标准答案，无个性化评价 | AI 出题 + 四维可解释评分 + 错题间隔复习 |
| AI 简历工具 | 在线简历生成 | 只排版不深挖 JD，无匹配度量化 | 解析简历 + 解析 JD + 匹配度打分 + 缺失技能清单 |
| AI 面试产品 | 部分商业化产品 | 一次性生成 N 轮问题，**不是真对话**；反馈笼统 | 一问一答真对话、HR 逐字流式回复、按简历深挖 |
| 直接问通用大模型 | ChatGPT 类 | 黑盒、无参照、无评分体系、无追踪 | 全链路可观测 + 结构化 rubric + 长期画像与历史回溯 |

## 3. 核心创新点

> 答辩时这四个点要能各用一句话讲清。

### 创新点一：显式建图的 Agentic 编排 + 全链路 SSE 可观测

**做法**：用 LangGraph 显式建了 **9 张状态图**（不是黑盒 Agent 框架），每个节点在开始和结束各推一条**同 id** 的结构化事件，经 SSE 实时流到前端「执行面板」，从「进行中」原地变成「已完成 + 耗时」。

**价值**：
- 用户看得见 Agent 在干什么 —— 这是产品层面的差异化，不是技术炫技
- 事件是结构化数据（`{id, type, status, payload, duration_ms}`），前端可以按类型渲染成不同组件，而不是塞一段日志文本
- 同一套事件机制同时服务于「用户体验」与「工程调试」

**技术难点**：每个模块的 Agent 执行都要流式化，而不是等跑完一次性出结果。详见 [06-可观测设计.md](./06-可观测设计.md)。

### 创新点二：四维 rubric 可解释评分

**做法**：评分强制走四个维度，各 0–5 分，**每个维度必须给出评分理由**，结构化 JSON 输出，**禁止返回裸分数**。

| 维度 | 权重 | 考察什么 |
|---|---|---|
| 正确性 | 0.40 | 结论是否正确、有无硬伤 |
| 完整性 / 深度 | 0.30 | 是否覆盖要点、能否深入机制 |
| 表达与结构 | 0.15 | 逻辑是否清晰、是否结构化表达 |
| 术语准确性 | 0.15 | 专业术语使用是否准确 |

**价值**：
- 用户知道「扣在哪、怎么改」，而不是一个孤零零的分数
- 评分量表天然是 0–5，**可以直接当作间隔重复算法（SM-2）的输入**，两套机制无缝对接
- 有明确量表就意味着**人工能标注 ground truth**，指标可量化 —— 这是后续微调评测的前提（见创新点三）

### 创新点三：数据飞轮 —— 系统自己长出自己的微调数据集

**做法**：每次评分都往 `answers` 表写一条 `(题目, 参考答案, 用户作答, 四维评分 JSON)`。这**本身就是一条 SFT（监督微调）样本**。攒够之后导出、LoRA 微调一个小模型，专门学会按四维 rubric 输出结构化 JSON。

```
用户刷题 → 评分落库(answers) → 导出脚本 → SFT 数据集 → LoRA 微调
   ↑                                                        │
   └────── 本地小模型替代云端大模型评分 ←── vLLM 起服务 ←────┘
```

**价值**：**不用另找数据集**。用户每做一次评分，训练集就长一条。这是本项目在「大模型微调」课程主题上最自然的落点，也是整个系统里**唯一能拿出「微调前 vs 微调后」对比表**的地方。

> **当前状态**：训练与评测的**代码件已全部完成**（数据导出脚本、评测脚本、LLaMA-Factory 训练配置、评测集模板），但**数据集尚未导出、人工标注评测集尚不完整、LoRA 尚未训练**。
> 具体进度与待执行清单见 [09-模型微调方案.md](./09-模型微调方案.md)。

### 创新点四：运行时热配置 —— 模型与检索策略后台可改、改完即时生效

**做法**：把模型端点、模型名、温度、检索模式、召回条数、精排开关、查重阈值、LLM 网关配置全部做成数据库里的 key-value 配置项，由管理后台编辑。LangGraph 节点**每次执行读一次**配置，所以改完立即生效，**不用改代码、不用重启服务**。

**价值**：
- 演示「同一问题、不同召回策略」的对比时，切一下开关就行
- 把 Base URL 指向本地 vLLM 服务即可从云端切到本地，这是「部署」实验的基础设施
- `.env` 仍是唯一事实来源（库里只存「覆盖」），不会出现两处配置打架
