# 01 · 需求分析

> 需求的权威来源是 `PRD-ai-interview-platform.html`（v0.9）第 4、5、12 章。本篇不重复 PRD 的需求描述，
> 而是把需求**编号化、加上实现状态、并建立到设计章节的追溯关系** —— 让读者一眼看出「哪条需求落到了哪里、落到什么程度」。

---

## 1. 用户角色与使用场景

### 1.1 角色定义

| 角色 | 说明 | 关键诉求 |
|---|---|---|
| **求职者**（主要用户） | 计算机方向在校生 / 应届生，正在准备技术岗面试 | 想知道自己答得好不好、简历能不能过、面试会问什么 |
| **管理员** | 系统运营者 / 课程助教 | 维护题库质量、管理用户、调整模型与检索策略 |

### 1.2 求职者的三条核心场景

**场景一：定向刷题**

> 「我投的后端岗，B+ 树索引这块比较虚。想练几道中级题，做完想知道自己差在哪。」

关键需求：能按方向 / 难度 / 题型筛题 → 能写自己的答案（不是选择题）→ 能得到**分维度的**评价 → 能针对薄弱点继续追问 → 答错的题以后要能想起来复习。

**场景二：简历诊断**

> 「我要投这个 JD，但不确定我的简历够不够格。」

关键需求：上传 PDF → 粘贴 JD → 得到匹配度 + 缺什么技能 + 简历怎么改。

**场景三：模拟面试**

> 「想找人对练但找不到人。想要真的像面试一样一问一答，最后告诉我哪轮答得不好。」

关键需求：**真对话**（不是一次性生成 N 轮）→ 提问要贴着自己的简历（考察是不是真做过项目）→ 结束后有结构化报告。

## 2. 功能性需求与实现状态

> 编号体系沿用 PRD 第 4 章。**状态四态说明**：
> `已完成` = 代码实现且链路可用；`已实现待实测` = 代码完整但缺实测数据；`部分实现` = 只落了主干，有明确缺口；`规划中` = 尚未实现。

### 2.1 FR-A 刷题模块

| 编号 | 需求 | 实现状态 | 落点 |
|---|---|---|---|
| FR-A1 | 出题条件选择（方向 / 难度 / 题型 / 薄弱点） | 已完成 | 前端 `/practice` 页；方向为后端 / 前端 / 算法，难度为入门 / 中级 / 高级，题型为八股 / 算法 / 业务 |
| FR-A2 | AI 生成题目（含参考答案与考察点） | 已完成 | `generate_question_graph`（检索 → 生成 → 查重三节点） |
| FR-A3 | 题目去重（避免与题库重复） | 已完成 | `dedup_node` 用向量相似度比对，阈值 0.90，超阈值则回边重生成，最多 3 次 |
| FR-A4 | 题源混合（题库检索 + 模型生成） | 部分实现 | 检索节点把相似题作为**参考**喂给生成模型（prompt 里明确「仅避免重复，不要照抄」），**尚未实现「直接复用题库原题」这条路径** |

### 2.2 FR-B 作答评测与追问

| 编号 | 需求 | 实现状态 | 落点 |
|---|---|---|---|
| FR-B1 | 作答输入（长文本） | 已完成 | 前端文本框，可提交长作答 |
| FR-B2 | 多维评分 | 已完成 | 四维 rubric：正确性 0.40 / 完整性 0.30 / 表达 0.15 / 术语 0.15，各 0–5 分 |
| FR-B3 | 生成参考答案 | 已完成 | `GradeOutput.reference_answer` 字段 |
| FR-B4 | 上下文追问（1–3 轮） | 已完成 | `followup_graph`，针对薄弱点 / 遗漏点 / 表述模糊处追问 |
| FR-B5 | 可解释性（说明扣分理由） | 已完成 | 每个维度都必须带 `reason` 字段，禁止返回裸分数 |

> **重要设计事实**：四维权重**只写在 prompt 文本里**（`prompts.GRADE_RUBRIC`），服务端**不做加权校验**，`total_score` 由模型自报。这是一个有意识的取舍 —— 加权计算由模型完成可以省一次校验调用，代价是无法防御模型算错总分。若需要严格保证，应在服务端按四维重算总分并比对。详见 [05-Agentic-RAG设计.md](./05-Agentic-RAG设计.md) 第 5 节。

### 2.3 FR-C 收藏 / 错题 / 训练报告

| 编号 | 需求 | 实现状态 | 落点 |
|---|---|---|---|
| FR-C1 | 收藏题目 | 已完成 | `answers.is_favorite` + `PATCH /answers/{id}` |
| FR-C2 | 错题本 | 已完成 | `answers.is_wrong`（总分 < 3.0 判错）+ 错题本页面三个标签页（待复习 / 错题 / 收藏） |
| FR-C3 | 回答存档 | 已完成 | `answers` 表；列表联表带出题目信息，避免前端 N+1 查询 |
| FR-C4 | 训练报告 | 已完成 | `training_report_graph` → 总体评价 / 薄弱点 / 改进建议 / 雷达数据 |
| FR-C5 | 能力分析 | 部分实现 | `SkillProfile` 表与 upsert 接口已实现，但**缺少「刷题 / 面试后自动更新画像」的逻辑** —— 目前需要前端显式调用 `POST /report/profile` |
| FR-C6 | 雷达图数据 | 已完成 | 训练报告雷达四维 = 正确性 / 完整性 / 表达 / 术语 |

### 2.4 FR-D 简历优化

| 编号 | 需求 | 实现状态 | 落点 |
|---|---|---|---|
| FR-D1 | PDF 解析 | 已完成 | `pypdf` 逐页提取文本；不做 OCR，扫描件返回 400「无法从 PDF 提取文本，可能是扫描件」 |
| FR-D2 | JD 输入 | 已完成 | 前端文本框，与简历一同提交 |
| FR-D3 | 匹配分析 | 已完成 | `diagnose_graph`，输出匹配度 0–100 + 亮点 + 短板 + **缺失技能清单** |
| FR-D4 | 优化建议 | 已完成 | 按结构 / 措辞 / 量化 / 关键词 / 项目描述五个方向分点给出 |
| FR-D5 | 简历草稿生成 | 规划中 | 未实现。当前只给建议，不生成改写后的简历文本 |

> **实现细节**：`/resume/diagnose` 是**串行三次 LLM 调用**（解析简历 → 解析 JD → 对比诊断），不是一次调用完成。这样拆的理由是每一步的产物都可单独复用（简历结构化结果可直接用于面试模块），代价是延迟叠加。

### 2.5 FR-E 模拟面试

| 编号 | 需求 | 实现状态 | 落点 |
|---|---|---|---|
| FR-E1 | 面试配置（方向 / 难度 / 风格） | 已完成 | 存在 `interview_sessions.config_json`，含 direction / difficulty / style / resume 快照 |
| FR-E2 | HR 提问 | 已完成 | **一问一答真对话**：`/interview/chat/stream` 三合一入口（建会话 / 续聊 / 总结） |
| FR-E3 | 实时评分 | **未按原设计实现** | 改为「结束时统一出报告」而非逐轮实时打分，理由见下方说明 |
| FR-E4 | 参考答案 | 部分实现 | 面试提问图（`interview_question_node`）会生成 `reference_answer` + `key_points`，但**一问一答对话路径不产出逐轮参考答案** |
| FR-E5 | 面试报告 | 已完成 | `interview_report_graph`：总分 0–100 + 总体评价 + 逐轮评价 + 改进建议 + 能力雷达 |
| FR-E6 | 追问策略（项目深挖 / 技术栈深挖 / 压力测试三种风格） | 部分实现 | 三种 style 已接入 prompt，但是**通过对话自然追问**而非按固定轮次策略执行 |

> **FR-E3 的设计变更说明**：PRD 原设计是「每轮实时评分」。实际实现改为对话结束后一次性生成报告，原因是：面试中的实时打分会让 HR 的回复带上评判语气，破坏对话真实感（`INTERVIEW_CHAT_SYSTEM` 明确要求「不主动打分」）；且逐轮打分需要每轮多一次模型调用，成本翻倍。面试报告雷达的四个维度也相应改为**技术深度 / 项目经验 / 表达沟通 / 问题解决**（区别于训练报告的四维）。

| 编号 | 需求 | 实现状态 | 落点 |
|---|---|---|---|

| FR-F2 | 不暴露原始思维链 | 已完成 | 事件只推「工具名 / 模型名 / 阶段 / 命中数量 / 耗时」等结构化字段，不推模型的推理文本 |
| FR-F3 | 可回溯 | 部分实现 | 前端轨迹通过 `usePageState` 在会话内保留；**服务端不落 `tool_traces` 表**，刷新后轨迹丢失（该表已建但无读写路径） |

### 2.7 FR-G 账户与数据（横切）

| 编号 | 需求 | 实现状态 | 落点 |
|---|---|---|---|
| FR-G1 | 认证（注册 / 登录 / 当前用户） | 已完成 | JWT（HS256，有效期 24 小时）+ bcrypt 密码哈希 |
| FR-G2 | 数据隔离 | 已完成 | 所有用户数据强制 `user_id` 过滤；跨用户访问返回 **404 而非 403** |
| FR-G3 | 用量配额 | **规划中** | 未实现。当前无每日配额、无限流、无超时熔断 |
| FR-G4 | 内容安全 | **规划中** | 未实现。无提示注入防护、无输出内容审核 |

> **FR-G2 的细节**：单条查询的实现方式是「取回后比对 `user_id`」而不是 WHERE 过滤；列表查询才是 SQL 级过滤。跨用户访问返回 404 的理由是**避免泄露记录是否存在** —— 若返回 403，攻击者可以通过状态码差异枚举出哪些 id 真实存在。详见 [04-数据模型设计.md](./04-数据模型设计.md) 第 5 节。

### 2.8 管理员端（PRD 一期的非目标，实际已实现）

PRD 第 1.3 节明确把「管理员端」列为一期**非目标**。实际实现中**已经做完了**，属于超出原范围的工作量：

| 能力 | 说明 |
|---|---|
| 用户管理 | 列表 / 关键词搜索 / 设为或取消管理员 / 重置密码 / 删除；**不能取消或删除自己**（后端拦截） |
| 题库管理 | 分页 + 关键词 + 方向筛选；新建 / 编辑 / 删除**同步 Qdrant 向量库** |
| 模型与检索配置 | 12 项运行时配置，改完即时生效 |
| 概览统计 | 用户数 / 题目数 / 管理员数 / 近 7 天新增 / 各方向题目分布 |

## 3. 非功能性需求与达成情况

> 指标定义取自 PRD 第 5 章。**实测数据只有云端 LLM 压测一份**，其余指标为「设计目标 / 未验证」，如实标注。

### 3.1 性能

| 指标 | PRD 目标 | 实测 / 现状 |
|---|---|---|
| 评分与追问**首 token 延迟** | < 3 s | **云端实测 TTFT P50 = 2752.8 ms 达标**；P95 = 4278.4 ms 超出 |
| 评分与追问**总延迟** | 全程流式（未设总延迟目标） | 云端实测总延迟 P50 = 3741.6 ms、P99 = 5550.7 ms |
| 向量检索延迟 | < 500 ms（含 rerank） | **未单独测量** |
| 简历解析 / 报告生成 | 异步，接口 < 1 s 返回受理 | **未按此设计实现** —— 当前是同步 SSE 流，接口不立即返回受理，而是保持连接直到完成 |

> **压测口径**：`backend/benchmark/cloud-test.json`，模型 `deepseek-flash`，并发 4、总请求 8、prompt 200 字符、`max_tokens` 64、错误率 0%。样本量偏小（8 个请求），P95/P99 的置信度有限，作为基线参考而非容量结论。完整方法学见 [10-模型部署与网关.md](./10-模型部署与网关.md) 第 5 节。

### 3.2 成本

| PRD 要求 | 现状 |
|---|---|
| LiteLLM 追踪成本 | **未实现** —— `langfuse` 依赖已声明但代码零引用 |
| 小模型粗筛 + 大模型精判 | **未实现** —— 所有任务走同一个主生成模型 |
| 缓存命中降本 | **部分实现** —— `llm_session_id` 每请求生成并透传给网关，为 prompt 缓存亲和做了准备；但缓存是否命中未验证 |

### 3.3 可靠性

| PRD 要求 | 现状 |
|---|---|
| LLM 失败自动 fallback | **已实现** —— LiteLLM 网关配 `fallbacks` + `num_retries=2` + `timeout=120`；**网关配置写坏时静默回落直连**，不会因配置错误导致服务不可用 |
| 限流 | **未实现** |
| 指数退避重试 | **部分实现** —— 结构化输出校验失败时重试 1 次（共 2 次调用），无退避 |

### 3.4 安全与合规

| PRD 要求 | 现状 |
|---|---|
| JWT + RBAC | 已完成（JWT + `is_admin` 标记） |
| 用户级数据隔离 | 已完成（`user_id` 强制过滤，跨用户 404） |
| 简历 / 报告**静态加密** | **未实现** —— `resumes` 表 docstring 标注「敏感，需加密存储」，但实际无加密 |
| 传输 TLS | **未实现** —— 开发环境为 HTTP，CORS 用正则放行 localhost 任意端口 |
| 日志脱敏 | **未系统实现** —— 无统一脱敏中间件 |
| 采集告知 / 删除权 / 数据可导出 | **未实现** |

> **安全现状的自我评价**：当前安全能力集中在「认证」与「数据隔离」两件事上（这两件是硬性的、已做扎实），而「加密存储 / 脱敏 / 合规」三类属于生产化要求，尚未启动。完整清单与补齐路径见 [13-设计边界与演进规划.md](./13-设计边界与演进规划.md) 第 2 节。

### 3.5 可观测

| PRD 要求 | 现状 |

## 5. 验收标准

> 取自 PRD 第 12 章，转成可勾选的验收项。**勾选状态为当前实际达成情况。**

### 5.1 刷题模块

- [x] 能按方向 / 难度 / 题型选择并生成题目
- [x] 生成的题目不与题库重复（相似度 > 0.90 时自动重新生成，最多 3 次）
- [x] 题目含参考答案与考察点
- [x] 新题自动落库并同步向量库，后续出题可检索到

### 5.2 评分模块

- [x] 输出四个维度的分数，每维附评分理由
- [x] 输出改进建议与参考答案
- [x] 评分结果落库（`answers` 表）
- [x] 总分低于 3.0 自动标记为错题

### 5.3 错题与报告

- [x] 错题本可按「待复习 / 错题 / 收藏」三个维度筛选
- [x] 到期待复习的错题能正确取出
- [x] 复习后按 SM-2 重排下次到期时间
- [x] 连续答对 2 次移出错题本
- [x] 训练报告含总体评价、薄弱点、改进建议、能力雷达

### 5.4 简历模块

- [x] 能上传 PDF 并提取文本
- [x] 能解析简历为结构化数据（姓名 / 教育 / 技能 / 项目 / 工作 / 总结）
- [x] 能解析 JD 为结构化数据（岗位 / 职责 / 必备技能 / 加分技能）
- [x] 输出匹配度、亮点、短板、缺失技能、分点优化建议
- [ ] 生成改写后的简历草稿（**未实现**）

### 5.5 模拟面试

## 6. 需求变更记录

> 申报材料里体现「有意识地做了取舍」比「全部照做」更有说服力。

| 变更项 | PRD 原设计 | 实际实现 | 变更理由 |
|---|---|---|---|
| 面试评分时机 | 每轮实时评分 | 结束后一次性出报告 | 实时打分会让 HR 带上评判语气，破坏对话真实感；且每轮多一次模型调用，成本翻倍 |
| 面试报告维度 | 未明确 | 技术深度 / 项目经验 / 表达沟通 / 问题解决 | 面试考察的是综合表现，与刷题的四维 rubric 不是一回事 |
| 简历解析 / 报告生成 | 异步任务，接口 < 1 s 返回受理 | 同步 SSE 长连接流式 | SSE 已能提供「进行中」反馈，异步任务队列（ARQ）在一期属于过度设计 |
| 管理员端 | 一期非目标 | 已实现 | 题库质量直接影响 RAG 效果，没有后台无法运营；且运行时配置让「部署」实验成为可能 |
| 间隔重复 | 未要求 | 已实现 SM-2 | 刷题产品的核心留存机制，且四维量表天然对齐 SM-2 的 0–5 输入，实现成本极低 |
