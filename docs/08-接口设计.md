## 2. 认证与鉴权

### 2.1 JWT 设计

```python
def create_access_token(subject: str | int) -> str:
    expire = datetime.now(timezone.utc) + timedelta(
        minutes=settings.access_token_expire_minutes)
    payload = {"sub": str(subject), "exp": expire}
    return jwt.encode(payload, settings.jwt_secret, algorithm=settings.jwt_algorithm)
```

| 项 | 值 |
|---|---|
| 算法 | HS256（`settings.jwt_algorithm`） |
| 有效期 | **1440 分钟 = 24 小时**（`access_token_expire_minutes`） |
| payload 字段 | **只有 `sub`（用户 ID 字符串）与 `exp`** |
| 密钥 | `.env` 的 `JWT_SECRET`（默认 `"change-me"`，**生产必须改**） |
| 密码哈希 | bcrypt（passlib `CryptContext(schemes=["bcrypt"])`） |

**没有的东西（如实记录）**：没有 `iat`、没有 refresh token、没有 `jti` / 黑名单、没有服务端主动失效能力。

**影响**：token 泄漏后在 24 小时内持续有效；无法「强制下线」；没有续期机制，24 小时后必须重新登录。

**若需要改进**：引入 Redis 存黑名单（依赖与容器都已就绪），或改为「短 access token + refresh token」。

### 2.2 依赖注入

```python
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/api/v1/auth/login")

async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with async_session() as session:
        yield session

async def get_current_user(token = Depends(oauth2_scheme),
                           db = Depends(get_db)) -> User:
    """从 JWT 解析当前用户，失败抛 401。"""
    subject = decode_access_token(token)
    if subject is None:
        raise credentials_exc          # 401「认证失败，请重新登录」
    user = await user_repo.get_by_id(db, int(subject))
    if user is None:
        raise credentials_exc
    return user

async def get_current_admin(current_user = Depends(get_current_user)) -> User:
    """管理员专用：非管理员一律 403。"""
    if not current_user.is_admin:
        raise HTTPException(status_code=403, detail="需要管理员权限")
    return current_user

async def get_runtime(db = Depends(get_db)) -> dict[str, Any]:
    """读出管理员配置的运行时参数，注入 agent。"""
    return await settings_service.runtime_config(db)
```

| 依赖 | 作用 | 用在哪些端点 |
|---|---|---|
| `get_db` | 请求级数据库会话 | 几乎所有需要数据库的端点 |
| `get_current_user` | 认证 + 取用户，失败 401 | 全部需要登录的端点 |
| `get_current_admin` | 在 `get_current_user` 之上叠加管理员校验，失败 **403** | `admin.py` 全部端点 |
| `get_runtime` | 读出运行时配置注入 Agent | 全部流式端点的 `runtime` 参数 |

### 2.3 认证状态码语义

| 场景 | 状态码 | 文案 |
|---|---|---|
| 未带 token / token 无效 / token 过期 | **401** | 认证失败，请重新登录 |
| token 有效但用户已被删除 | **401** | 认证失败，请重新登录 |
| 已登录但非管理员访问 admin 接口 | **403** | 需要管理员权限 |
| 访问跨用户的资源 | **404** | 不存在或无权访问（见 §3.4） |
| 注册时邮箱已存在 | **400** | 该邮箱已注册 |
| 登录密码错误 | **400** | 邮箱或密码错误 |

> **一个安全细节**：登录失败统一返回「邮箱或密码错误」，**不区分「邮箱不存在」与「密码错误」** —— 否则会变成账号枚举接口。

## 3. SSE 流式接口契约

### 3.1 九个流式端点

| 端点 | 步骤事件 | 对话事件 |
|---|---|---|
| `POST /training/question/stream` | `检索` / `模型` | — |
| `POST /training/grade/stream` | `检索` / `模型` / `已记录` | — |
| `POST /training/followup/stream` | `模型` | — |
| `POST /resume/parse/stream` | `工具`（`pdf_extract`）/ `模型` | — |
| `POST /resume/diagnose/stream` | `工具` / `模型` | — |
| `POST /interview/question/stream` | `模型` | — |
| `POST /interview/chat/stream` | `模型` / `session` / `已记录` | **`token` / `hr_message`** |
| `POST /interview/report/stream` | `模型` | — |
| `POST /report/training/stream` | `模型` | — |

### 3.2 响应格式

```
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no

data: {"id":"retrieve:向量化","type":"检索","status":"running","payload":{"阶段":"向量化","模型":"BGE-M3"},"duration_ms":null}

data: {"id":"retrieve:向量化","type":"检索","status":"done","payload":{"阶段":"向量化","模型":"BGE-M3","query":"..."},"duration_ms":42}

data: [DONE]
```

**协议要点**：

| 项 | 值 |
|---|---|
| 事件帧格式 | **匿名 `data:` 帧**（无 `event:` 行、无 `id:` 行、无 `retry:`） |
| 事件边界 | `\n\n` |
| 序列化 | `json.dumps(..., ensure_ascii=False)`（中文不转义） |
| 结束标记 | `data: [DONE]\n\n`（注意是**包在 `data:` 里的字符串**） |
| 心跳 | **无**（长静默期可能被中间代理断开，已知边界） |

### 3.3 事件类型

| type | 结构 | 说明 |
|---|---|---|
| `模型` | `{id, type, status, payload, duration_ms}` | 一次 LLM 调用 |
| `检索` | 同上 | 一次检索步骤 |
| `工具` | 同上 | 一次工具调用 |
| `结果` | `{type, payload}` | 最终业务结果（**流末尾的最后一个业务事件**） |
| `错误` | `{type, payload: {message}}` | 异常降级 |
| `token` | `{type, id, payload: {text}}` | **无 `status` / `duration_ms`** |
| `hr_message` | `{type, payload: {content, turn}}` | **服务端消费，不上抛前端** |
| `session` | `{type, payload: {session_id}}` | 会话 id |
| `已记录` | `{type, payload: {answer_id, is_wrong}}` | 评分落库回执 |

**同 id 原地替换语义**：`status: "running"` 与 `status: "done"` 两条事件用**同一个 `id`**。前端按 id 做替换，所以一个步骤在面板里始终只占一行。

### 3.4 异常处理约定

```python
try:
    async for mode, chunk in g.astream(...):
        ...
except Exception as exc:
    yield {"type": "错误", "payload": {"message": str(exc)}}
    return
```

**流式端点不会返回 5xx**：因为异常发生时 HTTP 响应头（状态码 200）已经发出，无法更改。所以异常必须降级为一条 `错误` 事件，前端据此设置错误状态并终止事件循环。

**非流式端点遇到异常则是正常的 500**。

### 3.5 前端消费方式

前端**不用 `EventSource`**（它只支持 GET 且不能自定义请求头），而是手写 `fetch` + 流式读取：

```ts
const res = await fetch(`${API}${path}`, { method: "POST", headers, body });
const reader = res.body.getReader();
const decoder = new TextDecoder();
let buffer = "";
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const chunks = buffer.split("\n\n");
  buffer = chunks.pop() ?? "";
  for (const chunk of chunks) {
    const line = chunk.trim();
    if (!line.startsWith("data:")) continue;
    const data = line.slice(5).trim();
    if (data === "[DONE]") return;
    try { yield JSON.parse(data); } catch { /* 跳过 */ }
  }
}
```

**四个必须处理的细节**：按 `\n\n` 切分事件、用 `buffer` 暂存跨 chunk 的不完整数据、`{stream: true}` 避免中文多字节被截断、解析失败静默跳过。

> 完整的前端状态机设计见 [06-可观测设计.md](./06-可观测设计.md) 第 5 节。

## 4. 错误码与状态码语义

### 4.1 状态码约定

| 状态码 | 使用场景 | 说明 |
|---|---|---|
| **200** | 普通成功 | 包括流式端点的「已经开始流」 |
| **201** | 资源创建成功 | 仅 `POST /auth/register` |
| **400** | 业务校验失败 | 邮箱已注册、密码错误、未知模块、不能删除自己、文件为空 |
| **401** | 未认证 | token 缺失 / 无效 / 过期 / 用户不存在 |
| **403** | 无权限 | **仅用于「非管理员访问管理员接口」** |
| **404** | 资源不存在**或无权访问** | 跨用户访问也返回 404，见 §4.2 |
| **500** | 服务端异常 | 非流式端点的未捕获异常 |

### 4.2 为什么跨用户访问返回 404 而不是 403

| 状态码 | 攻击者能推断出什么 |
|---|---|
| 403 | 「这个 id 存在，只是不属于我」→ **可以枚举出哪些 id 真实存在** |
| **404** | 「这个 id 对我不可见」→ **无法区分「不存在」与「存在但无权」** |

因此所有跨用户访问（作答、面试会话、历史记录）一律返回 **404**，错误文案统一为「不存在或无权访问」，不区分两种情况。

**这是一个有意的信息隐藏设计**：用状态码的一致性换取存在性信息的不可推断性。

### 4.3 错误响应格式

FastAPI 的默认错误格式：

```json
{"detail": "该邮箱已注册"}
```

Pydantic 校验失败时 `detail` 是数组：

```json
{"detail": [{"loc": ["body", "email"], "msg": "field required", "type": "value_error.missing"}]}
```

前端的处理方式是优先取 `body.detail`（字符串），若为数组则取 `detail[0].msg`。

**统一异常处理器**：**未实现**。目前完全依赖 FastAPI 的默认行为，没有自定义 `@app.exception_handler`。这意味着数据库异常等内部错误会把原始信息透给客户端。生产环境应加统一处理器，把内部错误转成通用文案并记日志。

## 5. 关键接口的请求 / 响应示例

### 5.1 评分（流式端点的请求体）

```http
POST /api/v1/training/grade/stream
Authorization: Bearer <token>
Content-Type: application/json

{
  "question": "请讲讲 HashMap 的底层实现原理。",
  "reference": "JDK8 的 HashMap 采用「数组 + 链表 + 红黑树」结构……",
  "answer": "底层是数组加链表，哈希冲突用链表解决，JDK8 之后链表长了会变成红黑树。",
  "question_id": 2
}
```

`question_id` **必须提供才能落库**；缺失时评分仍然返回，但不会写入 `answers` 表，末尾也不会推 `已记录` 事件。

末尾的两条事件：

```
data: {"type":"结果","payload":{"correctness":{"score":4,"reason":"..."}, ... ,"total_score":4.1, ...}}

data: {"type":"已记录","payload":{"answer_id":17,"is_wrong":false}}
```

### 5.2 面试对话（三合一入口的三种用法）

**开新面试**：

```json
{"direction": "后端", "difficulty": "中级", "style": "项目深挖",
 "resume": {"name": "...", "skills": ["Java", "MySQL"], "projects": [...]}}
```

返回事件序列：`session` → `模型/running` → N×`token` → `模型/done` → `结果`。

**发言**：

```json
{"session_id": 3, "message": "我用的是双链表加哈希表实现 LRU……"}
```

**总结**：

```json
{"session_id": 3, "summarize": true}
```

返回：`模型/running` → `模型/done` → `结果`（payload 含报告）。

> 服务端会用库里 `config_json` 的配置**覆盖请求里的配置** —— 也就是说续聊时不需要重复传 `direction` / `resume` 等参数，传了也会被库里的值覆盖。会话不存在或不属于当前用户时推一条 `错误` 事件：「面试会话不存在或无权访问」。

```json
]
```

**`kind` 的五个取值**：`text` / `select` / `bool` / `number` / `secret`（另有 `textarea` 用于 JSON 配置）。

| 字段 | 含义 |
|---|---|
| `overridden` | 管理员是否改过（`True` 表示库里有覆盖记录，`False` 表示用的是 `.env` 默认） |
| `has_value` | **仅 `secret` 类有** —— 表示「已设置过密钥」，但不回显内容 |
| `options` | 仅 `select` 类有 |

**`secret` 类的处理**：`default` 与 `value` **都被置为空字符串**，只提供 `has_value`。理由写在代码里：「后台页面是发给浏览器的，密钥一旦进了响应体就等于泄给了任何一个能打开这个页面的管理员会话。」

**提交时的语义**：`kind == "secret"` 且值为空字符串时**跳过该项**（表示「不修改」）。这让管理员可以在不回显密钥的前提下改其他配置。

### 5.4 历史记录快照

```json
POST /api/v1/history
{
  "module": "practice",
  "title": "后端 · 中级 · 八股：HashMap 底层实现",
  "snapshot": { "...": "页面状态的完整快照" },
  "session_id": null
}
```

`module` 必须是 `practice` / `resume` / `interview` / `report` 之一。**快照的字段名必须与前端页面状态对象的字段名逐字一致** —— 恢复时是整块覆盖，key 对不上就恢复不出来（详见 [07-核心业务模块设计.md](./07-核心业务模块设计.md) 第 6 节）。

## 6. CORS 策略

```python
app.add_middleware(
    CORSMiddleware,
    allow_origin_regex=r"http://(localhost|127\.0\.0\.1)(:\d+)?",
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

| 项 | 值 | 理由 |
|---|---|---|
| 允许的 origin | **正则**匹配 localhost / 127.0.0.1 的任意端口 | Next 开发服务器在 3000 被占用时会自动顺延到 3001 / 3002，固定端口列表会让新端口上的每个请求预检都返回 400 |
| `allow_credentials` | `True` | 为将来的 Cookie 场景留余地（当前用 Bearer 头） |
| methods / headers | `*` | 开发期便利 |

**两条重要注意**：

1. **`allow_credentials=True` 时不能用 `allow_origins=["*"]` 通配**。正则方案同时满足「允许任意本地端口」与「不使用通配符」两个约束。
2. **生产环境必须收紧成真实前端域名** —— 这一点在代码注释里已明确标注。

## 7. 一个必须指出的实现缺陷

### 7.1 `GET /admin/llm/options` 重复定义

`app/api/v1/admin.py` 中同一个函数名与装饰器出现了两次：

| 位置 | 状态 |
|---|---|
| 第 229 行 | **死代码**（含一个 `fallback` 变量与三处 return） |
| 第 297 行 | **实际生效**（返回值多一个 `base_url` 字段） |

FastAPI 按装饰顺序注册路由，**同方法同路径的后注册者覆盖前者**。所以第一个函数永远不会被调用。

**影响**：
- 代码里有一段永不执行的逻辑，读者会困惑「为什么改这里没效果」
- 端点数统计口径混乱（48 个装饰器 vs 47 个有效端点）

**修正方式**：删除第 229 行起的第一处定义。

### 7.2 其他接口层面的已知边界

| 边界 | 影响 |
|---|---|
| 无统一异常处理器 | 内部错误（如数据库异常）会把原始信息透给客户端 |
| `/docs` 与 `/openapi.json` 未保护 | 全部端点暴露在 Swagger UI 中 |
| 无限流、无配额 | 无法防止单用户刷爆 API 额度 |
| 无请求 ID / 无访问日志中间件 | 排查问题时无法关联同一次请求的多条日志 |
| `POST /history` 的 `module` 校验是白名单硬编码 | 新增模块需要同时改前后端 |
