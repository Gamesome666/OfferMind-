# OfferMind 技术方案

> **可观测 Agentic RAG 驱动的 AI 求职面试训练平台**
>
> 大模型部署与微调 · 课程设计 + 竞赛项目 · 用户端（一期）· 计算机方向求职

---

## 一句话读懂项目

OfferMind 给计算机方向的求职者提供**四条训练闭环**（定向刷题 / 简历诊断 / 模拟面试 / 能力报告），四条闭环共享一份长期能力画像，全程由**可观测的 Agent 执行面板**贯穿 —— 用户能实时看到 Agent 在检索什么、调用什么模型、每一步花了多久。

**与直接用通用大模型的关键差别**：答案是**有参照的**（RAG 检索题库）、评分是**可解释的**（四维 rubric，每维带理由）、过程是**可见的**（全链路 SSE 事件）、结果是**可追溯的**（历史记录 + 错题间隔复习）。

---

## 核心卖点

| # | 卖点 | 一句话说明 |
|---|---|---|
| 1 | **显式建图 + 全链路可观测** | 9 张 LangGraph 状态图，每个节点推同 id 的结构化事件，执行面板里每一步「进行中 → 已完成 + 耗时」原地更新 |
| 2 | **四维可解释评分** | 正确性 0.40 / 完整性 0.30 / 表达 0.15 / 术语 0.15，各 0–5 分，**每维必须给出理由**，禁止裸分数 |
| 3 | **数据飞轮** | 每条评分记录就是一条 SFT 样本 —— 系统的副产品即训练资料，用本地小模型替代云端大模型评分 |
| 4 | **运行时热配置** | 模型端点 / 模型名 / 温度 / 检索模式 / 网关全在后台可改，**改完即时生效，无需重启** |
| 5 | **混合检索** | 稠密向量 + BM25 稀疏 + RRF 名次融合，三种模式后台可切换 |

## 技术栈速览

| 层面 | 选型 |
|---|---|
| AI 编排 | Python + **LangGraph**（9 张状态图） |
| RAG | LangChain + **Qdrant**（稠密/稀疏/混合三模式 + RRF 融合） |
| 本地模型 | **BGE-M3**（嵌入，1024 维）+ **bge-reranker-v2-m3**（精排） |
| 生成模型 | 云端 DeepSeek（可经 **LiteLLM 网关**路由到本地 vLLM） |
| 后端 | **FastAPI** + SQLAlchemy 2.0 async + asyncpg |
| 存储 | **PostgreSQL**（事务主数据）+ Qdrant（检索索引） |
| 前端 | **Next.js 15.1** + React 19 + TypeScript（零 UI 库依赖） |
| 部署 | Docker Compose（基础设施）+ vLLM（规划） |
| 微调 | LLaMA-Factory + LoRA（Qwen2.5-1.5B） |

## 实现状态总表

> 本套方案严格区分三种状态。**凡标注「待实测」的地方，只给表格骨架与执行方法，不填任何数字。**

### ✅ 已完成并验证

| 模块 | 内容 |
|---|---|
| 认证与隔离 | JWT + bcrypt；所有用户数据强制 `user_id` 过滤；跨用户返回 404 |
| 刷题闭环 | 出题（含查重与回退重生成）→ 四维评分 → 追问 → 自动入库 |
| RAG 检索 | 题库库落地；稠密 / 稀疏 / 混合三模式；RRF 融合；精排 |
| 错题本 | 完整 SM-2 间隔重复（含 ease 动态调整、连续答对毕业规则） |
| 简历诊断 | PDF 解析（`pypdf`）+ 简历/JD 结构化 + 匹配度诊断 |
| 模拟面试 | 一问一答真对话；HR 回复逐字流式；结束时生成报告 |
| 能力报告 | 训练报告 + 面试报告（两套不同雷达维度） |
| 可观测 | 9 个流式端点；5 字段事件协议；执行面板 + 对话分流 |
| 历史记录 | 快照回溯 + 跨路由页面状态保持 |
| 管理后台 | 用户管理 / 题库管理（同步向量库）/ 运行时配置 |
| LiteLLM 网关 | 进程内 Router；失败自动 fallback；**配置写坏静默回落直连** |
| 压测方法学 | 固定 prompt 长度、区分 TTFT 与总延迟、报 P50/P95/P99 |

### ⏳ 已实现待实测

| 项 | 现状 |
|---|---|
| **微调链路** | 导出脚本 / 评测脚本 / LoRA 配置全部完成；**数据集未导出、人工标注仅 2 条、LoRA 未训练、无对比数据** |

## 关于数据可信度的一条说明

本套方案对实验数据采取保守口径：

- 项目中**唯一真实的性能数据**是 `backend/benchmark/cloud-test.json`（云端 LLM 压测，8 请求 / 并发 4）。本方案在 [10 §5.5](./10-模型部署与网关.md) 引用它，并**明确标注样本量偏小、P95/P99 置信度有限**。
- `backend/finetune/eval/test_before.json` 与 `test_after.json` **是演示 `--compare` 输出格式的占位产物，不是实测结果**。其中 `test_after.json` 的指标与自身 `rows` 在数学上不自洽（预测值全为 0 却声称一致率 0.75）。**本方案不引用这两份文件中的任何数字。**
- 凡是标注「待实测」的表格，**只给骨架与执行方法**。

理由很简单：申报材料里的每一个数字都应当可追溯到原始产物文件。

## 一个重要的阅读提示

项目根目录的 `CLAUDE.md` 是 AI 协作指引，**其中有多处描述与代码实际不符**（例如把已实现的混合检索列为待办、把图的数量写成 8 张、把 `tools.py` 描述为空壳）。

**本套方案的所有技术事实以代码为准**，并在 [03-技术选型与论证](./03-技术选型与论证.md) 与各章节中记录了 14 处事实修正。若发现本套方案与 `CLAUDE.md` 冲突，以本套方案为准。
